03그라파나 — 이 화면을 이렇게 읽는다

시나리오 문서의 확인 전략이 "Grafana 대시보드를 이용하여 처리량·이벤트 식별을 진행"입니다. 그 대시보드(Embedded CDC Overview · CDC 검증 리포트)의 패널 다섯 개를 이번 실측 화면으로 설명합니다. 각 패널이 어떤 질문에 답하는지를 먼저 잡으면 나머지는 그림이 말해 줍니다.

패널 1 · 행 수 추이 — "커밋됐는가, 따라잡았는가"

위 02절의 첫 그림입니다. 읽는 규칙 세 가지 — ① source 의 수직 계단이 커밋 순간이고, ② target 의 추격 곡선 기울기가 적재 속도이며, ③ 두 선의 수평 간격이 그 시점의 지연입니다. 두 선이 다시 만나면 그 배치는 끝난 것입니다. 50만 건 구간을 확대하면 규칙이 더 선명합니다.

패널 2 · End-to-End 지연 — "예산 안인가, 그리고 이 수치를 믿어도 되는가"

source 커밋 시각과 target 반영 시각의 차입니다. 판정 규칙 — ① 예산선(5초)과 비교하고, ② 반드시 시계 편차 게이트(허용 0.5초)가 열려 있는지 함께 보며(이번 전 구간 1~5 ms), ③ Timer max 는 피크 후 스스로 내려가므로 피크 직후에 읽고, 연속 배치에서는 이전 피크의 잔영을 의심합니다.

패널 3 · 연산별 처리량 — "지금 흐르는 것이 INSERT 인가 UPDATE 인가"

시나리오 문서의 질의 그대로 sum by (table, op)(rate(cdc_events_total[..])) 입니다. op 레이블 r/c/u/d 로 스냅샷·적재·수정·삭제가 갈라져 보입니다. 읽는 규칙 — ① 어느 색 산인지로 연산을 식별하고, ② 산 높이로 그 연산의 처리 속도를, ③ 같은 산을 1분 창이 4~5배 눌러 보여주므로 버스트 판정은 15초 창으로 합니다.

패널 4 · Replication Slot 지연 — "컨슈머가 얼마나 밀렸는가" (V2 관점)

슬롯이 붙잡고 있는 WAL 양입니다. V2 는 이 패널을 "다운 중"에 봤지만, 이번 실측이 보여주는 것은 컨슈머가 살아 있어도 배치 중에는 밀린다는 사실입니다. 읽는 규칙 — ① 산 높이 = 그 배치가 만든 최대 밀림, ② 산이 0 으로 돌아오면 따라잡은 것, ③ 산 높이를 경보 임계(warn 512 MB)와 견줍니다.

패널 5 · 대사 판정식 — "다 끝난 뒤, 정말 같은가" (V6 관점)

시나리오 문서의 확인 전략 abs(cdc_source_rows − cdc_target_rows) 에 DLQ 보정을 더한 판정식입니다. 읽는 규칙 — 이 선은 0 이어야 정상이고, 배치 중에는 일시적으로 뜨는 것이 정상입니다. 0 으로 돌아오지 않는 것만이 문제입니다.

INSERT / UPDATE / DELETE 이벤트가 도착하는가 (V1)통과세 연산 모두 10만 건 규모에서 전량 도착 — op 레이블로 각각 식별(03절 패널 3)

05고려할 것

고려 사항내용
1. 예산 5초의 실질 경계는 1만 건이다지연은 배치 크기 ÷ 적재 상한(~8,200/s)으로 예측된다. 1만 건은 회차에 따라 73~171%를 오가는 경계선이고 5만 건부터는 항상 초과다. 실제 업무에 1만 건 초과 단일 트랜잭션이 존재하는지가 V1 판정을 가른다 — 존재하면 예산 상향 / 원천 배치 분할 / 적재 경로 개선 중 택일(기존 V1 결론과 동일, 이번에 경계가 숫자로 확정)
2. UPDATE 는 감사 비용으로 절반 속도다UPDATE 10만이 2,872/s 로 INSERT(8,013/s)의 36%. car 에 켜진 필드 변경 감사가 이벤트당 INSERT 한 건을 더 쓰기 때문(감사 10만 행 실측). V1 의 "감사는 테이블별로만, 보관 정책과 함께" 결론이 처리량 수치로 실증됐다 — UPDATE 가 많은 표에 감사를 켤 때는 이 절반 속도를 용량 계획에 넣어야 한다
3. 슬롯 밀림은 다운이 아니라 배치에서도 생긴다컨슈머가 살아 있어도 배치 중 슬롯이 92.6 MiB 까지 밀린다(V2 는 다운 중만 봤다). 슬롯 lag 경보 임계(warn 512 MB)는 정상 배치의 산 높이보다 넉넉히 위에 있어야 배치마다 오탐이 나지 않는다 — 업무 최대 배치 크기 확정 후 재환산
4. Timer max 잔영 — 연속 배치의 함정이전 배치의 지연 피크가 감쇠 중에 다음 배치 판정에 겹쳐 보인다(S5·S6 의 60.5초가 그것). 연속 배치 상황에서 lag_max 하나로 판정하면 틀린다 — 반영 완료 소요(행 수 추이 두 선이 만나는 시각)로 교차 판정해야 한다
5. 커밋은 병목이 아니다50만 건 커밋도 1.42초. 시간을 쓰는 곳은 target 적재(JDBC 멱등 UPSERT)다. 개선 투자를 한다면 원천이 아니라 적재 쪽이다

06개선 — 이번 실측이 가리키는 것

개선근거와 방법
원천 배치 분할 가이드1만 건 이하로 쪼개 커밋하면 각 조각이 예산 안에 든다(적재 총량은 같으므로 전체 소요는 유지). 원천 배치 작업에 "커밋 단위 ≤ 1만" 규칙을 문서화
감사 로그 보관 정책 선행UPDATE 절반 속도 + 감사 표 무한 증가(기존 측정: 243만 행에서 처리량 1,177 → 283/s). 파티셔닝/보관 기간 확정 전에는 감사를 켤 표를 늘리지 않는다
슬롯 lag 경보 임계 재환산"정상 배치 산 높이 × 여유 배수"로 산정. 지금 값(512 MB)은 50만 건 배치(97 MiB) 기준으로는 적정 — 업무 배치가 더 크면 같이 커져야 한다
배치 반영 완료 지표Timer max 잔영을 우회하는 판정 — "source 와 target 행 수가 다시 같아진 시각"을 지표/패널로 상시화(행 수 추이 패널을 수치로 읽는 것)
UPDATE 경로 적재 튜닝 검토감사 INSERT 를 본 UPSERT 와 같은 배치에 묶는지 확인 — 분리돼 있다면 왕복이 두 배다. 코드 확인 후 판단

07재현 절차

각 단계는 "SQL 한 번 → target 추격 완료 대기 → Prometheus 피크 스냅샷" 순서로 돌았습니다.

# 단계 실행 (car 표) — INSERT 는 generate_series 한 문장 = 한 트랜잭션
INSERT INTO car (name, brand, price)
SELECT 'car-'||to_char(now(),'YYYYMMDDHH24MISS')||'-'||g, ..., ...
  FROM generate_series(1, {건수}) AS g;

# UPDATE / DELETE 도 한 문장
WITH pick AS (SELECT id FROM car ORDER BY id LIMIT 100000)
UPDATE car SET price = ..., updated_at = now() WHERE id IN (SELECT id FROM pick);

# 반영 완료 판정 — target 행 수가 source 와 같아질 때까지 2초 간격 폴링
SELECT count(*) FROM car;   -- source · target 양쪽

# 단계 종료 후 Prometheus 피크 스냅샷 (창 W = 단계 소요 + 45s)
max_over_time(cdc_end_to_end_lag_seconds_max{table="car"}[Ws])
max_over_time((sum(rate(cdc_events_total[15s])))[Ws:5s])
max_over_time(cdc_slot_lag_bytes[Ws])

# 최종 정합 — 건수 + md5 체크섬 (양쪽 동일 질의)
SELECT count(*) || '|' || md5(string_agg(id::text||name||brand||price::text, ',' ORDER BY id)) FROM car;

재현할 때 흔들리는 것

Timer max 감쇠 — 연속 배치 사이 간격이 짧으면 이전 피크가 겹친다(판정은 반영 완료 소요로). 감사 설정 — car 감사가 꺼져 있으면 UPDATE 처리량이 이 보고서보다 높게 나온다. 표 크기 — 회차를 이어 돌리면 UPSERT 대상 표가 커져 적재 상한이 서서히 낮아질 수 있다(이번 실측은 3행에서 시작).

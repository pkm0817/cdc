    디스크는 계단으로 찹니다

    223 B 는 순수 CDC 비용이 아닙니다

    10분 다운 중 원천에서 autovacuum 2회 · autoanalyze 4회 · 요청 체크포인트 1회가 돌았습니다. 이들이 쓴 WAL 도 슬롯이 붙잡으므로 "변경 1건당" 에 섞입니다. 회차가 길수록 이 몫이 커져 186 → 200 → 223 B 로 오른 것으로 봅니다. 허용시간 산출에는 이 값이 오히려 맞습니다 — 실제 디스크를 채우는 것은 CDC 변경분만이 아니기 때문입니다. 반대로 "CDC 가 쓰는 비용" 을 말할 때는 이 값을 쓰면 과대평가입니다.

FULL 의 순수 대가는 UPDATE 한 행당 67 B 로 봅니다 — car 행의 실제 크기(약 70~90 B)와 맞아떨어집니다. 절대값 450 B 대가 큰 것은 CHECKPOINT 직후라 full-page write 가 양쪽에 똑같이 섞였기 때문이며, 차이를 볼 목적에는 문제가 없습니다.

    06측정 중 드러난 문제

    문제증상조치
    cdc_wal_size_bytes 미사용 수집은 되는데 화면에 없어 디스크 압력을 슬롯 lag 으로만 보고 있었다 패널 신설 (세 스택)
    "유실 0" 이 V2 섹션에 없었다 통과 기준의 절반이 V6 로 미뤄져 있었다 다운 후 정합 패널 신설
    mountpoint="/var/lib" 이 환경에서 한 번도 매칭된 적이 없어 늘 폴백으로 떨어졌고, 그 폴백은 "가장 큰 파일시스템" 을 집는다 데이터 디렉터리에 가까운 순서로 명시하고 루트로 마감
    비율 패널이 1000배 부풀었다 clamp_min(..., 0.001) 하한 탓에 부하가 끝나면 165 B 가 1017 KiB 로 보였다 흐를 때만 계산하도록 게이트
    슬롯 active 계열이 안 보였다 0/1 값이 bytes 축에 묻혀 있었다 오른쪽 축으로 분리

    측정 도중 스택이 재생성됐습니다

    08남은 결정 — 디스크 고갈이냐 재동기화냐

    V2 의 실질 결론입니다. 두 선택지의 대가를 숫자로 놓고 고르면 됩니다.

    A · 상한 없음 (-1, 현재)

    • 얻는 것 — 슬롯이 절대 무효화되지 않는다. 컨슈머가 살아 돌아오면 언제든 유실 0으로 따라잡는다
    • 잃는 것 — 허용시간이 "디스크 찰 때까지" 다. 넘으면 source DB 가 먼저 죽는다
    • 1만 변경/초에서 5.2일
    • safe_wal_size 가 NULL 이라 무효화 여유를 감시할 수 없다

    B · 상한을 건다 (권고: 디스크 여유의 20~30%)

    • 얻는 것 — 원천 DB 는 절대 죽지 않는다. safe_wal_size 로 여유를 상시 감시할 수 있다
    • 잃는 것 — 초과하는 순간 슬롯 무효화. V3 재동기화로 넘어간다
    • 200 GB 상한 · 1만 변경/초에서 약 27시간
    • 재동기화 절차가 준비돼 있어야 성립하는 선택지다 (V3)

    1GB 는 너무 작습니다

    시험 삼아 걸어본 1GB 는 이 실험의 74 변경/초에서도 18.2시간, 1만 변경/초면 8분 만에 소진됩니다. 상한을 건다면 값은 디스크 여유에 비례해 잡아야 하고, 그러려면 운영 변경 속도를 먼저 실측해야 합니다.

    09재현 절차

    한 회차가 도는 순서

    스냅샷을 다운 전후로 두 번 찍는 것이 요점입니다. 그 차이가 "다운 시간 D 초 동안 쌓인 WAL" 이고, 다운 중 30초마다 남기는 곡선이 선형성 판정의 근거입니다.

    다운 시간별 회차 · v2run.sh
    # 다운 D초 동안 초당 90건(INSERT 60 + UPDATE 30)을 넣고, 재기동 후 정합을 확인한다.
# 버스트가 아니라 일정 속도로 넣어야 WAL 증가량 차이가 다운 시간 탓임이 갈라진다.
bash v2run.sh   3 "down-2s"   v2.jsonl
bash v2run.sh  60 "down-60s"  v2.jsonl
bash v2run.sh 600 "down-600s" v2.jsonl   # 다운 10분 + 회복, 약 11분

# 각 회차가 남기는 것
#   v2.jsonl                     회차 요약 (유실 · 회복 · WAL)
#   v2-<라벨>-samples.csv        다운 중 30초마다 슬롯 보유 WAL (선형성 곡선)
    REPLICA IDENTITY 비교 · v2ri-clean.sh
    # UPDATE 문 하나만 재고, 직전 CHECKPOINT 로 구간을 끊는다.
# 이렇게 하지 않으면 autovacuum·체크포인트 WAL 이 신호만큼 섞인다.
ROWS=5000 REPS=3 bash v2ri-clean.sh v2ri-clean.jsonl

# 끝나면 반드시 FULL 로 되돌린다 (V5 요구). 스크립트가 마지막에 수행한다.
ALTER TABLE car REPLICA IDENTITY FULL;
    상한을 걸었을 때 safe_wal_size 확인
    ALTER SYSTEM SET max_slot_wal_keep_size = '1GB';
SELECT pg_reload_conf();          -- sighup 이라 재기동 불필요
SELECT safe_wal_size, wal_status FROM pg_replication_slots;
-- -1 일 때는 NULL, 상한을 걸면 실제 값이 온다

ALTER SYSTEM SET max_slot_wal_keep_size = -1;   -- 확인 뒤 되돌린다
SELECT pg_reload_conf();

    재현할 때 흔들리는 것

    배경 WAL — autovacuum 과 체크포인트가 회차마다 다르게 끼어듭니다. 회차를 여러 번 돌려 중앙값을 씁니다.
    워밍업 — 다운 첫 60초는 누적율이 낮게 나옵니다. 선형 구간만 회귀에 씁니다.
    표 크기 — 회차를 이어 돌리면 car 가 계속 커져 autovacuum 빈도가 달라집니다. 엄밀히 비교하려면 회차마다 초기화합니다.
    TSDB 보존 — Prometheus 를 재시작하면 그 전 구간이 사라질 수 있습니다. 스크린샷은 실험 직후에 받습니다.

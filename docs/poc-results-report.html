    세 스택은 완전히 분리돼 있습니다

    컨테이너·네트워크·볼륨·슬롯 이름·source DB 가 모두 따로입니다. 같은 SQL 을 세 source DB 에 각각 실행하므로 source 실행 시간은 스택마다 다른 값이고, 서로의 트래픽이 섞이지 않습니다. 대신 같은 호스트의 CPU와 디스크는 공유합니다.

    01무엇을 어떻게 읽었나

    "반영이 끝났다" 를 무엇으로 판정하는지가 모든 시간 값의 정의입니다.

    구간판정 기준사용한 지표주의
    커밋 완료source 행 수가 계단식으로 오른 시점cdc_source_rows스크랩 간격 5초라 오차 ±5초
    반영 완료target 살아있는 행 수가 source 값에 도달한 시점cdc_target_rows소프트 삭제 표는 deleted = false 만 셈
    처리량행 수 ÷ (반영 완료 − 커밋 완료)위 두 값의 차분구간 평균이며 순간 최대가 아님
    지연변경 발생 시각부터 target 반영까지cdc_end_to_end_lag_seconds스택 간 직접 비교 금지 — 기준 시각이 다름
    정합성건수 + md5 체크섬 + 키 연속성cdc_source_rows − cdc_target_rows건수만으로는 값 변조를 못 잡음(V6 에서 실증)

    지연 지표로 두 스택을 비교하면 안 됩니다

    Debezium 은 커밋 시각(source.ts_ms)을, go-pq-cdc 는 WAL 송신 시각(MessageTime)을 기준으로 삼습니다. 09-02 화면에서 Java 6.67분 대 Go 2.50분으로 보였지만, 같은 배치의 실제 반영 완료 시각 차이는 10초였습니다. 스택 비교는 행 수가 같아지는 시각으로만 합니다.2

    버스트는 rate([1m]) 로 판정하지 않습니다

    1만 건을 6.7초에 처리한 구간이 rate(cdc_events_total[1m]) 에서 255/s 로 보입니다. 창이 넓어 6분의 1로 희석됩니다. 추세 감시용으로는 맞지만 버스트 판정에는 [15s] 창이나 적재 완료 시각 직접 계산을 씁니다.

    병목은 캡처가 아니라 수신 적재입니다

    100만행 배치에서 source INSERT 자체는 35~40초인데 반영에 585~610초가 걸립니다. 두 스택 모두 4,900~6,300 행/초 띠 안에 머물고 배치마다 순위가 뒤집힙니다. 즉 상한을 정하는 것은 구현 언어가 아니라 target 의 UPSERT 속도입니다.2

    작은 배치에서는 Go 가 실제로 빠릅니다

    1만행 INSERT 에서 Java 10.9초 대 Go 7.0초(1.56배), DELETE 에서 8.9초 대 5.9초(1.51배)입니다. 다만 100·1,000행 구간의 2.2~2.6초는 처리 능력이 아니라 고정 지연이므로 처리량 비교에 쓰지 않습니다.3

    연산 종류는 지연을 만들지 않습니다

    30만행 기준 source 실행이 INSERT 6,565ms 에서 DELETE 1,107ms 로 6분의 1인데, CDC 반영은 213.5초 대 212.1초로 같습니다. 파이프라인 비용은 연산 종류가 아니라 이벤트 개수가 정합니다. 원천 WAL 비용은 다릅니다 — INSERT 366 bytes/행, UPDATE(FULL) 493, DELETE(FULL) 128 입니다.

    05V1~V6 검증 결과

    확인 전략 문서7의 통과 기준을 그대로 옮기고, 그 옆에 실제 계측치6를 붙였습니다. V1 상세는 별도 보고서에 있습니다5.

    V1 · 기본 캡처 — 통과 기준: 목표 지연 5초 이내 + 필드 단위 변경 식별

    Java
    왕복 지연 INSERT 522ms · UPDATE 519ms · DELETE 502ms. 시계 편차 286~329ms 로 허용치(500ms) 안이라 세 회차 모두 유효합니다. UPDATE 에서 [amount, status] 두 필드만 변경으로 잡혔고, 1만 건 배치는 10,000/10,000 수신에 캡처 처리량 3,789 events/s 입니다.
    Go
    같은 필드 [amount status] 를 식별했고 1만 건 10,000 수신. 지연은 2~5ms 로 찍히지만 기준 시각이 송신 시각이라 Java 값과 같은 축이 아닙니다.
    판정
    둘 다 통과 다만 1만 건 버스트의 최대 지연이 4.97초로 5초 예산의 99% 였습니다. 여유가 거의 없습니다.

    V2 · Provider 다운 — 통과 기준: 유실 0건 + 다운 허용시간 산출

    측정
    다운 2.4초 동안 1,000건 변경 후 재기동해 1,000/1,000 수신, 유실 0건. 슬롯이 붙잡은 WAL 161.9 KiB, 변경 1건당 165 bytes 입니다.
    미결
    다운 허용시간이 아직 숫자로 안 나옵니다. 산출식(디스크 여유 ÷ WAL 증가율)의 두 항은 지표로 만들어 두었으나 (node_filesystem_avail_bytes 933GB, rate(cdc_wal_lsn_bytes_total)), max_slot_wal_keep_size = -1 이라 상한이 "디스크가 찰 때까지" 입니다. 상한을 걸지 말지가 V2 의 실제 결론입니다.
    주의
    165 bytes/변경 은 REPLICA IDENTITY FULL 기준입니다. V5 요구가 V2 압력을 키우는 구조입니다.

    V3 · 캡처 연결고리 끊김 — 통과 기준: 유실 자동 탐지 + 재동기화 절차

    Java
    슬롯 강제 삭제 후 끊긴 구간 100건 중 0건 수신. 엔진이 예외를 내고 종료했고 SlotContinuityGuard 도 탐지했습니다. 재동기화 후 101/101 복원됐습니다.
    Go
    같은 상황에서 라이브러리가 새 슬롯을 만들고 조용히 이어서 돕니다. 탐지는 전적으로 가드 몫이며, 가드가 탐지에 성공했습니다.
    미결
    PostgreSQL 16 은 논리 슬롯을 standby 로 승계하지 않습니다. 페일오버하면 슬롯이 무조건 사라지므로 이 시나리오가 재현됩니다. 승계는 PostgreSQL 17 의 sync_replication_slots 부터입니다. 확인할 항목을 "생기는지" 가 아니라 "페일오버 후 재동기화에 얼마나 걸리는지" 로 바꿔야 합니다.
    미결
    재적재만으로는 정합이 안 맞습니다. 원본에서 사라진 행은 멱등 UPSERT 로 지워지지 않으므로, 절차에 "target 에만 남은 행 처리" 단계를 넣어야 합니다.

    V4 · 중복 유입 — 통과 기준: 중복 유입에도 최종 정합 유지

    측정
    ack 전에 정지시켜 중복을 만든 뒤 재기동. 200건 재유입 중 200건이 같은 LSN 이었고 1차 반영 200행 · 2차 반영 0행, 두 번 반영된 행 0건입니다.
    미결
    표마다 방어 기제가 다릅니다. source_lsn 가드가 걸린 표는 순서 역전까지 막지만, 가드 없는 표는 늦게 온 오래된 이벤트가 최신 값을 덮어쓸 수 있습니다. 실제 대상 표에 가드를 걸지 정하고 V4 를 표별로 돌려야 합니다.
    미결
    DLQ 재처리도 중복 유입 경로인데 아직 시나리오에 없습니다. 격리 후 정상 경로로 같은 행이 갱신된 상태에서 재처리하는 경우를 넣어야 합니다.

    V5 · 이벤트가 비어서 오는 경우 — 통과 기준: 관심 필드가 항상 판독 가능

    Java
    REPLICA IDENTITY DEFAULT 에서 after 에 __debezium_unavailable_value 자리표시자가 와서 판독 불가. FULL 로 바꾸면 before·after 양쪽에 200,000 bytes 가 온전히 실립니다.
    Go
    DEFAULT 에서는 컬럼 자체가 실리지 않습니다. FULL 로 바꾸면 라이브러리가 old 이미지 값으로 메워 주므로 after 로 바로 읽힙니다.
    미결
    FULL 의 대가를 아직 안 쟀습니다. DEFAULT 대비 WAL 증가율을 같은 부하로 비교하고, 대용량 필드가 없는 표까지 FULL 로 둘지 표별로 판단해야 합니다. 판별법은 정해 두었습니다 — select max(pg_column_size(컬럼)) 이 TOAST 임계 약 2KB 를 넘는 컬럼이 후보입니다.

    V6 · 최종 안전성 — 통과 기준: 인위적 유실 주입 시 대사에서 검출

    측정
    정상 상태 300/300 체크섬 일치. 3건을 지웠을 때 불일치 검출, 행을 지우지 않고 금액만 1 올렸을 때도 검출됐습니다. 건수 대사만으로는 부족하다는 것이 실험으로 확인됐습니다.
    heartbeat
    heartbeat.interval.ms 만 켜면 관심 표에 변경이 없을 때 슬롯 전진이 0 bytes 입니다. heartbeat.action.query 를 같이 걸어야 33,440 bytes 전진합니다. go-pq-cdc 는 표 하나 지정으로 둘을 한꺼번에 합니다.
    미결
    DLQ 건수를 대사식에 넣어야 합니다. 격리된 건은 유실이 아니라 추적되는 미반영이므로 판정식은 source − target − DLQ(PENDING) = 0 이 맞습니다.
    미결

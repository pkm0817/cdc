    V4 이중 반영 — 중복은 두 경로로 들어오고, 막는 힘은 테이블마다 다르다

    「PoC CDC 기술 검토 - 시나리오」의 V4 에서 결론은 났지만 검증에 들어가 있지 않던 두 가지를 이번에 넣고 실제로 돌린 결과입니다. 하나는 DLQ 재처리라는 두 번째 중복 유입 경로이고, 다른 하나는 테이블마다 다른 방어 기제입니다. 그 둘을 겹쳐 보니 한 테이블이 실제로 되돌아갔습니다.

    이번에 확인된 사실

    • 중복 유입 경로는 둘이다 — 오프셋 되감기(재기동)와 DLQ 재처리
    • 재처리는 "중복"이 아니라 역전이다. 격리 뒤 정상 경로로 값이 바뀌어 있을 수 있다
    • source_lsn 가드가 있는 세 테이블은 0행 반영으로 막았다
    • 가드가 없는 car 는 격리 시점 값으로 되돌아갔다

    그래서 정해야 할 것

    • 실제 대상 테이블에 가드를 걸지 말지 — 걸지 않으면 DLQ 재처리를 쓸 수 없다
    • DLQ 재처리 결과에 반영 행 수를 남길지 — 지금은 차단과 반영이 같은 RESOLVED 다
    • 가드 없는 테이블의 재처리를 막을지 경고만 할지

    한 문장으로

    V4 는 "중복이 와도 괜찮은가"가 아니라 "누가 그것을 막고 있는가"의 문제였습니다. 막는 주체는 파이프라인이 아니라 각 테이블의 UPSERT 문장이고, 그래서 테이블마다 답이 다릅니다.

    01이번 회차 범위

    시나리오 문서의 V4 에서 결론은 적혀 있으나 코드·검증에 반영되지 않은 두 항목만 다뤘습니다2.

    시나리오 문서의 지적이전 상태이번 회차
    테이블마다 방어 기제가 달라서 하나만 보고 통과시키면 안 됨. V4 를 테이블별로 돌릴 것 검증 전용 verify_sink 한 표만 사용. 그 표에는 LSN 가드가 있어 항상 통과 운영 4개 테이블 각각에 대해 실제 저장소 구현으로 시나리오 수행
    DLQ 재처리도 중복 유입 경로인데 지금 V4 가 안 보고 있음 미검증. DeadLetterReprocessor 는 있으나 시나리오가 없음 격리 → 원인 수정 → 그 사이 정상 경로 갱신 → 재처리 전 구간 재현

    이번에 하지 않은 것

    • car 에 가드를 추가하는 코드 변경 — 업무 판단이 먼저다
    • DLQ 재처리 결과에 반영 행 수를 남기는 기능 — 발견만 하고 조치는 다음 회차
    • V1·V2·V3·V5·V6 의 미결 항목 (각 회차 보고서 참조)

    측정 환경

    • PostgreSQL 16 → Debezium Embedded 3.6.1 → PostgreSQL 16, Kafka 없음
    • java 스택 단독 기동 — go·cdc-custom 스택은 내리고 측정
    • 스택을 새로 올린 직후 상태에서 시작 (스냅샷 car 3 / computer 3 / grade 5 / member 5)

    이 시나리오만 운영 테이블을 쓴다

    다른 검증은 verify_* 전용 표와 전용 슬롯으로 돌지만, V4-b 가 확인하려는 것이 각 테이블의 저장소 구현과 운영 DLQ 재처리기 자체입니다. 복제본을 만들면 정작 운영에서 쓰는 경로가 검증되지 않습니다. 그래서 기동 중인 emb-cdc-service 와 운영 테이블을 그대로 쓰고, 넣은 행은 시나리오 끝에서 원천·수신 양쪽에서 지웁니다.

    읽는 법

    중복이 왔지만 반영되지 않았다는 것이 통과의 내용입니다. "중복 수신 0" 이 목표가 아닙니다 — 그것을 목표로 삼으면 애초에 재현할 수 없는 조건을 검증하게 됩니다.

    다만 이 회차에서 한 번 실패했습니다

    스택을 새로 올린 첫 실행에서 재기동이 The connector is trying to read change stream starting at … but this is no longer available on the server 로 거부됐습니다. 되돌린 오프셋 지점이 그 사이 전진한 슬롯 restart_lsn 보다 뒤였기 때문입니다. 같은 테스트를 다시 돌리면 통과합니다(이후 2회 연속 통과).

    이것은 테스트 결함이라기보다 V4 와 V3 의 경계입니다. 되감을 지점이 슬롯 안에 남아 있으면 V4(중복)이고, 슬롯 밖으로 밀려나면 그 순간 V3(복구 불가 구간)이 됩니다. 운영에서 이 경계를 결정하는 값이 max_slot_wal_keep_size 이며, 지금은 -1 입니다1.

    03두 번째 중복 유입 경로 — DLQ 재처리

    격리된 건은 유실이 아니라 추적되는 미반영입니다. 운영자가 원인을 고치고 status = 'RETRY_REQUESTED' 로 표시하면 재처리기가 그 이벤트를 다시 적용합니다. 문제는 격리와 재처리 사이의 시간입니다 — 그 사이 같은 행이 정상 경로로 이미 갱신돼 있을 수 있습니다.

    재처리가 역전이 되는 자리

    왜 이 그림이 필요한가

    재처리기는 이벤트를 다시 넣을 뿐이고, 그것이 안전한지는 ⑥ 다음의 마름모에서 갈립니다. 그 마름모는 파이프라인이 아니라 각 테이블의 UPSERT 문장 안에 있습니다. 문장에 조건절이 없으면 마름모 자체가 없습니다.

    배경
    수신 스키마가 원천과 같은 테이블에는 source_lsn 컬럼이 없다. 컬럼이 없으니 조건절도 없고, DLQ 재처리가 최신 값을 덮어쓴다.
    선택지 A
    가드를 건다. 수신 테이블에 source_lsn 컬럼을 추가하고 UPSERT 를 조건부 네이티브 문장으로 바꾼다. 대가는 "원천과 같은 스키마"라는 성질을 잃는 것과, 재적재·마이그레이션 시 그 컬럼을 채워야 한다는 것.
    선택지 B
    가드 없는 테이블은 재처리 대상에서 뺀다. 재처리기가 그런 테이블을 만나면 적용하지 않고 PENDING 으로 두어 사람이 확인하게 한다. 대가는 그 테이블의 격리 건이 자동으로 풀리지 않는 것.
    선택지 C
    그대로 두고 문서화한다. 재처리 전에 "그 사이 변경이 없었는지" 확인하는 절차를 운영 수순에 넣는다. 대가는 그 확인이 사람의 기억에 의존한다는 것.
    권고
    실제 대상 테이블이 소프트 삭제를 쓰는지와 함께 판단할 것. 소프트 삭제를 강제할 수 있는 테이블이라면 이미 부가 컬럼을 받아들인 것이므로 A 가 자연스럽고, 원천 스키마를 못 건드리는 테이블이라면 B 가 안전하다. C 는 재처리 빈도가 아주 낮을 때만.

    06부수 발견

    1. DLQ 상태만으로는 "반영됨"과 "차단됨"을 구분할 수 없다

    재처리기는 예외가 났는지로만 성패를 가릅니다. 가드에 막혀 0행이 반영돼도 예외는 없으므로 RESOLVED 가 됩니다. 이번 측정에서 네 테이블이 모두 RESOLVED 였지만, 실제로 값이 바뀐 것은 car 하나뿐입니다.

    이것이 왜 문제인가

    운영자가 재처리를 신청한 이유는 그 건을 반영하기 위해서입니다. 그런데 결과가 "막혔음"일 때도 화면에는 "해결됨"으로 보입니다. 가드가 정상 동작한 것과 재처리가 실제로 성공한 것은 다른 사건이고, 그 둘이 구분되지 않으면 "왜 아직도 값이 안 바뀌었지"를 사후에 추적할 수 없습니다.

    조치 제안 — 핸들러의 반영 행 수를 재처리 결과까지 올려 RESOLVED 와 SUPERSEDED(더 새로운 값이 이미 있어 반영하지 않음)를 나눌 것.

    2. V4 재기동 시나리오는 슬롯 위치와 경합한다

    02 절에 적은 첫 실행 실패입니다. 되돌린 오프셋이 슬롯 밖으로 밀려나면 V4 가 아니라 V3 상황이 됩니다. 검증 관점에서는 재실행으로 해결되지만, 운영 관점에서는 이것이 곧 다운 허용시간의 다른 얼굴입니다 — 되감을 수 있는 폭이 곧 슬롯이 붙잡고 있는 WAL 의 폭입니다.

    V2 와 이어지는 지점

    max_slot_wal_keep_size 를 -1 에서 유한한 값으로 바꾸면 디스크는 안전해지지만, 그 상한이 곧 "중복으로 복구 가능한 최대 폭"이 됩니다. 상한을 넘는 순간 슬롯이 무효화되어 V3 로 넘어갑니다. 두 값은 따로 정할 수 없습니다.

    07남은 판단과 조치

    검증은 끝났습니다. 남은 것은 기술이 아니라 업무 판단이 필요한 항목들입니다. 항목을 클릭하면 체크 상태가 브라우저에 저장됩니다.

    V4 안에서 남은 판단 0 / 0

    • 실제 대상 테이블에 순서 가드를 걸지 결정 (필수 · 선행)05 절의 선택지 A/B/C 중 하나. 이 결정 없이는 DLQ 재처리를 운영 수순에 넣을 수 없다
    • 가드 없는 테이블의 재처리를 막을지 경고만 할지막으면 격리 건이 자동으로 풀리지 않고, 경고만 하면 사람이 놓칠 수 있다
    • 재처리 결과에 반영 행 수를 남길지RESOLVED 와 SUPERSEDED 를 나눈다. 핸들러 반환값 변경이 필요해 인터페이스가 바뀐다
    • max_slot_wal_keep_size 상한 확정 (V2 와 공동)그 값이 곧 "중복으로 복구 가능한 최대 폭"이다. 넘으면 V3 가 된다

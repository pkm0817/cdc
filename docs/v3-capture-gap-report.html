    V3. 캡처 연결고리 끊김 — 탐지는 되고, 복구 절차에 한 단계가 빠져 있었습니다

    통과 기준은 둘입니다. 유실 발생을 자동 탐지, 그리고 재동기화 절차 문서화. 슬롯을 강제로 삭제하니 끊긴 100건 중 0건이 도착했고, 앱이 스스로 알아채 지표와 경보로 올렸습니다. 재동기화도 정합을 복원했습니다. 다만 두 가지가 문서에 없던 채였습니다 — 재적재만으로는 원본에서 지운 행이 target 에 남고, 오프셋 파일만 지워서는 파이프라인이 다시 뜨지 않습니다.

    간접 탐지로는 못 잡습니다

    슬롯이 사라진 상태에서 up{job="cdc-service"} = 1 이었습니다. 앱은 살아서 스크랩에 응답하고 엔진만 뜨지 않습니다. "스크랩이 실패하면 문제" 로 감시했다면 이 상황은 조용히 지나갑니다 — 대시보드에서는 "이벤트가 안 오네" 정도로만 보입니다. 앱이 직접 내는 cdc_capture_gap 이 필요한 이유가 이것입니다.

    실패한 첫 시도

    이중화 페일오버는 측정하지 않았습니다

    PostgreSQL 16 은 논리 복제 슬롯을 standby 로 동기화하지 않으므로 페일오버하면 슬롯은 반드시 사라집니다. "생기는지 확인" 할 일이 아니라 이미 정해진 결과입니다. 승계해 주는 sync_replication_slots 는 PostgreSQL 17 부터라, 이 항목에서는 버전 선택이 곧 대응책입니다. 슬롯이 사라진 뒤의 동작은 위 01절(강제 삭제)과 같으므로, 이 문서는 그것으로 갈음하고 복구 소요만 실측했습니다. standby 를 세운 실제 전환 측정은 별도 과제로 남깁니다.

    기동 거부를 HALT 로 셀 것인가

    시나리오 문서는 "HALT / 기동실패 카운터를 추가하고 경보 연결" 을 요구했습니다. 현재 구현은 둘을 나눠 놓았습니다 — 런타임 정지는 cdc_pipeline_halts_total, 기동 거부는 cdc_capture_gap 게이지입니다. 경보는 양쪽 다 붙어 있어 놓치는 상황은 없습니다. 다만 "몇 번 거부됐나" 는 셀 수 없습니다(게이지라 재시작 루프에서도 1 로 평평합니다). 재시작 루프의 횟수는 changes(process_start_time_seconds[15m]) 로 봅니다. 기동 거부에도 카운터를 하나 올릴지는 결정이 필요합니다.

    재현할 때 흔들리는 것

    lost 도달 — unreserved 에서 lost 로 가려면 체크포인트가 필요합니다. 그냥 기다리면 안 갈 수 있습니다.
    스냅샷 시간 — 복구 후 첫 이벤트까지의 시간은 표 크기에 비례합니다. 10만 행에서 18.6초였습니다.
    경보 for 절 — CdcSlotWalUnreserved 는 for: 1m 이라 짧은 실험에서는 pending 에 머뭅니다. firing 까지 보려면 상태를 1분 이상 유지해야 합니다.
    되돌리기 — max_slot_wal_keep_size 를 -1 로 복원하고, 무효화된 슬롯은 pg_drop_replication_slot() 으로 지운 뒤 복구 절차를 돌립니다.

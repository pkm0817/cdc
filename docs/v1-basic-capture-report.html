    V1. 기본 캡처 기능 — 단건은 통과했고 버스트는 예산을 넘겼습니다

    통과 기준은 두 개입니다. 목표 지연 5초 이내, 그리고 필드 단위 변경 식별. 단건 INSERT · UPDATE · DELETE 는 셋 다 예산의 10% 남짓으로 통과했고 변경 필드도 식별됩니다. 다만 같은 스택에 1만 건을 한 번에 넣으면 지연이 5.36~8.55초로 예산을 넘습니다 — 세 회차를 재서 세 번 다 예산의 99% 이상을 썼고 두 번은 넘겼습니다. 이 문서는 그 두 결과를 같은 무게로 기록하고, 판정에 쓰는 값이 화면·경보·검증 코드에서 같은 것을 가리키도록 맞춘 내용을 남깁니다.

    통과한 것

    • INSERT · UPDATE · DELETE 가 0.5초대로 도착한다. 예산 5초의 10% 남짓이다
    • UPDATE 에서 바뀐 필드가 [amount, status] 로 식별되고 값도 판독된다
    • 1만 건을 넣어도 유실 0건, LSN 단조 증가로 순서가 보존된다

    걸린 것 하나

    • 1만 건을 한 번에 넣으면 지연이 5.36~8.55초가 되어 예산을 넘는다 (재측정 2회 모두)
    • 문서에 기록된 4.97초도 이미 예산의 99.4% 였다 — 세 번 재서 세 번 다 여유가 없었다
    • 시계 편차 1ms 로 게이트를 통과했으므로 시계 문제가 아니라 실제 지연이다 (03절 근거)

    그래서 정해야 하는 것 하나

    1만 건 버스트가 실제 업무 부하에 존재하는가. 존재한다면 예산 5초는 이 구성으로 지켜지지 않으므로, 예산을 늘리든 원천 배치를 쪼개든 적재 경로를 손보든 셋 중 하나를 골라야 합니다(08 절). 존재하지 않는다면 V1 은 통과이고, 버스트 지연은 용량 계획의 참고값으로만 남깁니다.

    00범위와 전제

    V1 이 답하는 질문과, V1 로는 답할 수 없어 다른 항목으로 넘긴 질문을 먼저 갈라 둡니다.

    이 문서가 답하는 것

    • 관심 테이블의 INSERT / UPDATE / DELETE 가 목표 지연 안에 도착하는가
    • UPDATE 이벤트에서 어떤 필드가 바뀌었는지 식별되는가
    • 1만 건을 한 번에 넣었을 때 밀리지 않는가
    • 위 판정을 상시로 내리는 지표·경보·화면이 같은 값을 보고 있는가

    이 문서가 답하지 않는 것

    • 다운 허용시간과 WAL 디스크 압력 — V2
    • 슬롯이 끊겼을 때의 탐지와 재동기화 — V3
    • 중복 유입 시 최종 정합 — V4
    • 대용량 필드가 비어 오는 경우 — V5 (다만 변경 필드 식별의 전제인 REPLICA IDENTITY FULL 은 V5 가 요구한 설정이다)
    • 원천 DB 와 앱을 다른 장비로 나눴을 때의 시계 편차 — 아래 08 절의 남은 결정

    전제 — 이 측정이 성립하는 조건

    원천 DB 와 cdc-service 가 같은 호스트에서 돌고 있습니다. 실측 시계 편차 0~1ms 는 그 결과이지 이 구성의 성질이 아닙니다. 별도 장비로 나누면 편차를 다시 재야 하고, 편차가 0.5초를 넘는 구간의 커밋 기준 지연값은 판정에 쓰지 않습니다(01 절). 전 테이블이 REPLICA IDENTITY FULL 인 상태에서 측정했습니다 — DEFAULT 면 before 에 PK 만 와서 변경 필드 비교 자체가 성립하지 않습니다.

    01통과 기준 — 5초 예산과 시계 편차 게이트

    시나리오 원문에 N초로 비어 있던 목표 지연을 숫자로 확정하고, 그 숫자를 검증 코드 · 경보 · 대시보드가 각각 따로 들고 있지 않도록 한 곳으로 모읍니다.

    목표 지연은 5초로 확정합니다

    검증 코드에 이미 LATENCY_BUDGET = 5초 가 박혀 있었습니다1. 새 숫자를 정하는 대신 그 값을 기준으로 삼고, 나머지 두 곳을 거기에 맞췄습니다.

    편차가 허용치를 넘으면 그 회차 지연값은 버립니다

    cdc_end_to_end_lag_seconds 는 원천 커밋 시각(DB 시계)과 target 반영 시각(앱 시계)의 차입니다. 두 시계가 어긋나면 그 편차가 지연으로 둔갑합니다. 1차 실행에서 실제로 그런 일이 있었습니다 — 편차 3,561ms 에 재려던 지연이 526ms 였으니 오차가 재려던 값의 7배였습니다4.

    게이트만 걸면 문제가 조용히 사라집니다

    "편차가 크면 지연 경보를 내지 않는다"만 구현하면, 시계가 틀어진 구간에서 지연 경보가 아예 뜨지 않아 "지연 없음"으로 읽힙니다. 그래서 판정을 못 하는 상태 자체를 CdcLatencyUnverifiable 경보와 지연 판정 가능 여부 패널로 따로 세웠습니다. 둘은 배타적입니다 — 지연이 예산을 넘었을 때, 편차가 작으면 앞의 것이, 크면 뒤의 것이 뜹니다.

    이 편차는 회차마다 달라집니다. 검증 하네스와 운영 프로브가 왕복 보정까지 같은 식을 쓰는데도1, 1차 실행 3,561ms · results.md 회차 329ms · 오늘 라이브 1ms 로 세 자릿수 범위를 오갔습니다. 고정된 오프셋이 아니라 그때그때 달라지는 값이므로, 한 번 재서 괜찮았다고 넘길 수 없고 측정할 때마다 같이 봐야 합니다.

    판정 경로

    박스를 끌어 배치를 바꿀 수 있습니다. 실패 경로는 점선입니다.

    지연이 예산을 넘었다는 사실만으로는 경보를 내지 않습니다. 편차 게이트를 한 번 더 통과해야 "실제 지연"이 되고, 통과하지 못하면 별도 경보로 갈라집니다.

    편차는 앱이 직접 잽니다

    SourceClockSkewProbe 가 30초마다 원천의 clock_timestamp() 를 왕복 보정해 잽니다 — 질의 직전·직후 로컬 시각의 중간값과 견줍니다. 보정하지 않으면 네트워크 왕복의 절반이 편차로 계상되어, 편차가 없는 환경에서도 수 ms 가 계속 찍힙니다2.

    폐기한 방법 — 앱 wall clock 대리 계산

    처음에는 process_start_time_seconds + process_uptime_seconds 로 앱 시계를 계산하려 했습니다. 틀렸습니다. JVM uptime 은 호스트 절전 구간을 세지 않아서, 컨테이너가 9시간 떠 있는데 uptime 은 4.96시간이었고 편차가 -16,480초로 나왔습니다. 스크랩 기준 경로(cdc_clock_epoch_seconds − timestamp())는 앱이 안 떠 있을 때의 대체 판정으로만 남깁니다(CdcClockSkewByScrape).
    SourceClockSkewProbe.java · 왕복 보정
    long before = System.currentTimeMillis();
long dbNowMs = /* SELECT (extract(epoch from clock_timestamp()) * 1000)::bigint */;
long after  = System.currentTimeMillis();

// 질의 직전/직후의 중간값과 견준다. 보정하지 않으면 왕복의 절반이 편차로 잡힌다.
long skewMs = dbNowMs - (before + after) / 2;
metrics.clockSkew(skewMs);

    04필드 단위 변경 식별 — 통과, 다만 전제가 있습니다

    통과 기준의 나머지 절반입니다. 지연은 지표가, 이쪽은 표가 답합니다.

    UPDATE 이벤트에서 [amount, status] 두 개만 검출됩니다. 건드리지 않은 biz_key · id 는 잡히지 않습니다. 값도 판독됩니다 — status: NEW → CONFIRMED, amount: 20000.00 → 22000.003.

    "안 잡힌다"는 걸러낸다는 뜻이 아닙니다

    이벤트에는 안 건드린 컬럼도 그대로 실려 옵니다. 목록에 없는 이유는 before 와 after 의 값이 실제로 같기 때문입니다. 판정식을 FieldDiff 로 빼서 검증 코드와 운영 코드가 같은 것을 쓰게 했습니다 — 갈라지면 검증 통과와 운영 기록이 서로 다른 말을 하게 됩니다5.

    지표가 아니라 감사 표에 남깁니다

    무엇을어디에왜
    바뀐 필드명과 before/aftercdc_change_audit 변경 필드명을 Prometheus 레이블로 쓰면 시계열이 (테이블 × 컬럼 조합) 수만큼 생겨 카디널리티가 터진다
    기록 건수만cdc_change_audit_rows_total{table} 레이블은 테이블까지만
    판정 실패identifiable = false "안 바뀜"이 아니라 "판정 못 함" — 그 테이블이 FULL 이 아니라는 신호

    전역 on/off 가 아니라 테이블 목록으로 받으며 기본값은 비어 있습니다(꺼짐). 이벤트당 INSERT 가 한 건씩 더 붙으므로 처리량·지연에 대가가 있기 때문입니다 (cdc.apply.audit-changed-fields).

    전제 — REPLICA IDENTITY FULL

    DEFAULT 로 바꾸면 before 에 PK 만 와서 비교 자체가 성립하지 않고, identifiable = false 로 떨어집니다. 이 설정은 V5 가 요구한 것이고, 같은 설정이 V2 의 WAL 압력을 키웁니다. V1 의 통과가 V2 의 비용 위에 서 있습니다.

    수치값무엇인가어디에 쓰나
    캡처 처리량 (적재 제외)3,789 /s 검증 하네스가 이벤트를 큐에 담기만 한 값. target 적재(JDBC upsert)가 빠져 있다 엔진 자체의 상한
    운영 처리량 · 15초 창592.69 /s 적재까지 포함. 스크랩 5초라 표본 3개버스트 판정
    운영 처리량 · 1분 창142.26 /s 같은 버스트를 4분의 1로 눌러 보여준다추세 감시

    1분 창으로 버스트를 판정하면 안 됩니다

    1만 건을 6.7초에 처리한 구간이 rate(cdc_events_total[1m]) 에서는 255/s 로 보였습니다(문서 기록). 오늘 재측정에서도 592.69 대 142.26 으로 4.2배 차이가 났습니다. 창이 이벤트가 없는 시간까지 평균에 넣기 때문입니다. 추세 감시에는 1분 창이 맞지만, "버스트에서 밀리지 않는가"라는 V1 질문에는 15초 창을 씁니다.

    세 수치는 서로를 대체하지 않습니다. 보고서에는 캡처 처리량과 운영 처리량을 나란히 적고, 운영 처리량은 창 크기를 함께 표기합니다.

    06상시 판정 화면 — 무엇을 어디서 읽나

    검증 스크립트는 한 번 돌고 끝납니다. 운영에서 같은 판정을 계속 내리려면 화면이 필요합니다6.

    패널쿼리무엇을 답하나
    End-to-End 지연 (최대)max(cdc_end_to_end_lag_seconds_max)예산 안인가
    예산 소진율 신규 max(...) / 5 * 100여유가 얼마나 남았나
    시계 편차 (앱 왕복 보정) abs(max(cdc_clock_skew_seconds)) or 스크랩 기준 지연 수치를 믿어도 되나
    지연 판정 가능 여부 신규 (편차) <= bool 0.5지금 판정이 성립하나
    운영 처리량 (15초 창)sum(rate(cdc_events_total[15s]))버스트에서 밀리지 않나
    필드 단위 변경 식별cdc_change_audit 조회무엇이 무엇으로 바뀌었나
    식별 불가 (before 없음)identifiable = false 건수FULL 이 아닌 테이블이 있나

    세 스택이 같은 화면을 봅니다

    Java(Debezium) · Go(go-pq-cdc) · Java custom(outbox) 세 스택의 V1 상단 stat 줄이 쿼리와 좌표까지 동일합니다. 지표 이름을 일부러 맞춰 놓았기 때문에 (cdc_events_total, cdc_end_to_end_lag_seconds, cdc_clock_skew_seconds) 같은 쿼리로 세 스택을 견줄 수 있습니다.

    지표가 만들어지는 경로

    위 줄이 데이터 경로, 아래 줄이 계측 경로입니다. 옅은 오렌지 둘(BatchApplier · SourceClockSkewProbe)이 이번에 화면을 위해 손댄 부분입니다. 점선은 프로브가 원천에 질의만 하고 파이프라인을 건드리지 않는다는 뜻입니다. 앱이 안 떠 있을 때 쓰는 exporter 대체 편차 경로는 그림에서 뺐습니다 — 01 절 본문 참조.

    07측정 중 드러난 문제

    V1 을 다시 훑으면서 나온 것들입니다. 전부 고쳤고, 무엇이 왜 틀렸는지 남깁니다.

    문제증상조치범위
    판정에 쓰는 편차 지표가 화면에 없었다 경보 게이트는 cdc_clock_skew_seconds 를 보는데 대시보드는 exporter 기반 대체 경로만 그렸다. 경보가 떠도 근거를 볼 수 없다 앱 지표를 1순위로, 대체 경로는 폴백으로세 스택
    10% 게이트가 경보에만 있었다 판정 불가 상태가 화면에 없어, 시계가 틀어지면 "지연 없음"으로 읽힌다 지연 판정 가능 여부 패널 신설세 스택
    처리량이 1분 창만 있었다 버스트가 4분의 1로 눌려 보인다 15초 창 stat + 두 창 겹친 그래프세 스택
    예산 여유를 볼 수 없었다 500ms(10%)와 4.97초(99%)가 같은 "통과"로 보인다 예산 소진율 패널 신설세 스택
    custom 스택에 편차 프로브가 없었다 지연 경보에 게이트가 없고 Unverifiable 짝도 없었다 프로브 이식 · 지표 이름 통일 · 경보 2건 신설cdc-custom
    colorMode: "thresholds" stat 패널에 없는 값이라 임계 색이 전부 무시되고 있었다. 171% 가 회색으로 찍혔다 "value"세 스택 × 25 패널
    color.mode: "value" color mode 에 없는 값이라 패널이 통째로 에러로 떴다 "thresholds"세 스택 × 8 패널

    낡아 있던 메모 한 건

    대시보드의 V1 메모에 "앱의 wall clock 을 내주는 기본 메트릭이 없다. 상시 관측으로 옮기려면 앱에 gauge 를 하나 노출해야 한다"고 적혀 있었습니다. SourceClockSkewProbe 가 이미 그 일을 하고 있으므로 사실이 아닙니다. 결론이 코드에는 반영됐는데 문서에는 반영되지 않은 경우입니다 — 교체했습니다.

    같은 종류가 더 없는지 전수 검사했습니다

    열거값 오타가 두 번 연속 나와서, Grafana 스키마에서 값이 정해진 자리를 훑는 검사기를 만들었습니다. 대시보드 9개를 돌려 위 두 건 외에 2건을 더 잡았습니다 — legendFormat 을 바꾸면서 override 이름을 안 고쳐 오른쪽 축 분리가 죽어 있던 패널입니다.

    08판정과 남은 결정

    통과 기준 대비 판정

    통과 기준판정근거
    INSERT 가 5초 안에 도착통과 왕복 522 ms · 편차 329 ms
    UPDATE 가 5초 안에 도착통과 왕복 519 ms · 편차 307 ms
    DELETE 가 5초 안에 도착통과 왕복 502 ms · 편차 286 ms
    변경 필드 식별통과 [amount, status] 만 검출
    1만 건 배치에서 밀리지 않음조건부 통과 10,000/10,000 · LSN 단조 증가
    다만 지연 5.36~8.55 s (예산 107~171%)

    "조건부 통과"로 적는 이유

    유실은 없고 순서도 보존됩니다. 그러나 지연 기준으로는 예산을 넘겼습니다. 시나리오 문서의 4.97초(99.4%)도 여유가 거의 없던 값이고, 오늘 재측정은 8.55초(171.0%)와 5.36초(107.1%)였습니다. 세 회차 모두 99% 이상입니다. 1만 건 버스트가 실제 업무 부하에 존재한다면 예산 5초는 이 구성으로 지켜지지 않습니다. 예산을 늘리든지, 원천 배치를 쪼개든지, 적재 경로를 손보든지 셋 중 하나를 정해야 합니다.

    남은 결정

    다른 스택과의 비교는 여기서 하지 않습니다

    Go(go-pq-cdc) 판은 INSERT 왕복 5ms / 캡처 처리량 114,942 events/s 로 자릿수가 다릅니다. 그러나 지연의 기준 시각이 다릅니다 — Debezium 은 커밋 시각(source.ts_ms), go-pq-cdc 는 WAL 송신 시각(MessageTime)을 줍니다. 커밋에서 송신까지의 시간이 Go 쪽 수치에는 빠져 있으므로 두 값을 직접 비교하면 안 됩니다. 스택 선택은 별도 문서(cdc-library-decision.html)에서 다룹니다.

    09재현 절차

    이 보고서의 숫자를 다시 만들어 내는 방법입니다. 명령 그대로 실행됩니다.

    1
    스택 기동
    source · target PostgreSQL, cdc-service, Prometheus, Grafana 를 올립니다.
    2
    검증 스크립트
    V1 계측치를 results.md 에 다시 씁니다.
    3
    버스트 재현
    1만 건을 한 번에 넣고 상시 지표를 읽습니다.
    4
    판정
    편차 게이트를 먼저 보고, 통과했을 때만 지연값을 씁니다.
    재현 명령 · src/embedded-cdc
    # 1. 기동
./scripts/up.sh

# 2. V1 검증 (results.md 와 JUnit 리포트가 갱신된다)
./scripts/verify.sh -Tests "V1*"
#    계측치 : dev/cdc-service/build/verification/results.md
#    리포트 : dev/cdc-service/build/reports/tests/test/index.html

# 3. 1만 건 버스트
INSERTS=10000 UPDATES=0 DELETES=0 TABLES=car ./scripts/load.sh -n 1

# 4. 상시 지표 읽기 (Prometheus)
#    판정 게이트를 먼저 본다. 0 이면 아래 지연값은 쓰지 않는다.
(abs(max(cdc_clock_skew_seconds)) or abs(max(cdc_clock_epoch_seconds{job="source-db"}
   - timestamp(cdc_clock_epoch_seconds{job="source-db"})))) <= bool 0.5

max(cdc_end_to_end_lag_seconds_max)              # 지연 최대
max(cdc_end_to_end_lag_seconds_max) / 5 * 100    # 예산 소진율 (%)
sum(rate(cdc_events_total[15s]))                 # 버스트 판정용
sum(rate(cdc_events_total[1m]))                  # 추세용 — 버스트 판정에 쓰지 말 것

    판정이 흔들리는 지점

    스크랩 간격 — 5초 기준으로 [15s] 가 표본 3개입니다. 간격을 늘리면 창도 같이 늘려야 합니다.
    같은 호스트 — 편차 0~1ms 는 이 구성의 산물입니다. 장비를 나누면 다시 재야 합니다.
    REPLICA IDENTITY — DEFAULT 로 바뀐 테이블이 하나라도 있으면 identifiable = false 로 떨어지고 변경 필드 식별이 그 테이블에서만 실패합니다.
    Timer 의 max — cdc_end_to_end_lag_seconds_max 는 시간이 지나면 스스로 내려갑니다. 버스트 직후에 읽어야 최댓값이 잡힙니다.

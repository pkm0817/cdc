    V5 빈 이벤트 — 걸리는지 판별하는 법과, 해소의 대가

    통과 기준은 하나입니다 — 관심 필드가 모든 이벤트에서 항상 판독 가능할 것. PostgreSQL 은 UPDATE 에서 바뀌지 않은 대용량 필드를 이벤트에 싣지 않을 수 있고, 그래서 이 "항상"은 조건부입니다. 「PoC CDC 기술 검토 - 시나리오」의 V5 에서 결론은 났지만 실행할 수 없던 두 가지를 이번에 채웠습니다. 하나는 관심 필드가 이 케이스에 걸리는지 판별하는 방법이고, 다른 하나는 REPLICA IDENTITY FULL 이 실제로 얼마를 무는지입니다. 재보니 지금 스키마에는 걸리는 컬럼이 하나도 없고, 그런데도 FULL 을 못 내리는 이유는 V5 가 아니라 V1 이었습니다.

    관심 필드가 걸리는지 판별하는 방법을 정해둬야 실행이 됨 재현과 측정은 끝. 다만 "우리 테이블이 걸리는가"에 답하는 절차가 없어 결론이 실행되지 않음 2단계 절차 확정 — 선별 질의(toast-candidates.sql) + 이벤트로 확정. 검증이 같은 파일을 읽어 돌린다
    FULL 로 바꿨을 때 대가가 얼마인지는 아직 안 재봄 "해소는 되지만 비용은 안 묻고 있음". DEFAULT 대비 비교 없음 같은 부하로 DEFAULT/FULL 을 나란히 측정 — 좁은 표·넓은 표 × INSERT/UPDATE/DELETE 12개 구간

    측정 방법

    구간마다 CHECKPOINT 를 걸어 full page image 조건을 맞춘 뒤, pg_current_wal_lsn() 차분으로 총량을, pg_stat_wal 로 레코드 수와 FPI 수를 함께 남겼습니다. WAL 은 클러스터 공용이라 유휴 잡음이 섞이므로 같은 대기 시간의 유휴 바닥값을 먼저 쟀고, 이번 회차에는 0 B 였습니다. 측정 대상 표는 autovacuum 을 꺼서 청소 작업이 비용으로 잡히지 않게 했습니다.

    02이미 통과해 있던 것 — 못 읽고, 바꾸면 읽힌다

    PostgreSQL 은 큰 값을 행 밖(TOAST)에 두고, UPDATE 에서 그 컬럼이 바뀌지 않았으면 WAL 에 새 값을 싣지 않습니다. Debezium 은 그 자리를 자리표시자로 채웁니다 — 이것이 이 항목의 판정 기준입니다1.

    REPLICA IDENTITY FULL 200,000 bytes 온전히 200,000 bytes 온전히 가능

    INSERT 는 원래 문제가 아니다

    INSERT 이벤트에는 대용량 필드가 항상 온전히 실립니다(200,000 bytes 확인). 문제는 UPDATE 에서 그 컬럼을 건드리지 않았을 때뿐입니다. 이 구분이 뒤에 나오는 비용 수치의 모양을 그대로 설명합니다.

    03판별 방법 확정 — 2단계 절차

    "우리 관심 필드가 걸리는가"에 답할 수 없으면 앞 절의 결론은 실행되지 않습니다. 정적 선별(SQL) 뒤 동적 확정(이벤트) 두 단계로 정했습니다.

    1단계만으로 확정하지 않는 이유

    토스터는 컬럼이 아니라 행 전체가 임계를 넘을 때 동작하고, 그때 가장 큰 속성부터 밖으로 내보냅니다. 따라서 임계보다 작은 컬럼도 행이 넓으면 밖으로 나갈 수 있습니다. 1단계는 보수적 선별이고, 확정은 이벤트가 합니다.
    1단계 — scripts/toast-candidates.sql (일부)
    SELECT t.table_name, t.column_name, t.data_type, /* ... */
       COALESCE(m.max_size, 0)         AS max_stored_bytes,
       COALESCE(m.max_size, 0) >= 2032 AS toast_candidate  -- TOAST_TUPLE_THRESHOLD
FROM toastable t
CROSS JOIN LATERAL (
    SELECT (xpath('/row/c/text()',
             query_to_xml(format('SELECT max(pg_column_size(%I))::bigint AS c FROM %I.%I',
                                 t.column_name, t.schema_name, t.table_name),
                          false, true, '')))[1]::text::bigint AS max_size
) m
ORDER BY toast_candidate DESC, max_stored_bytes DESC;

    검증이 이 파일을 그대로 읽어 돌린다

    테스트가 같은 질의를 따로 들고 있으면 운영자가 손으로 돌리는 것과 갈라집니다. V5ReplicaIdentityCostTest 는 scripts/toast-candidates.sql 을 읽어 실행하고, 그 결과가 실제 이벤트 동작을 예측하는지까지 확인합니다 — 후보로 집힌 컬럼만 자리표시자로 오고, 집히지 않은 컬럼은 정상 판독됩니다.

    전 행 스캔이라 큰 테이블에서는 비쌉니다. 상시 모니터링이 아니라 스키마가 바뀔 때 돌리는 점검용으로 씁니다.

    656배가 나오는 이유

    DEFAULT 에서 그 컬럼을 건드리지 않은 UPDATE 는 TOAST 포인터를 그대로 재사용하므로 WAL 에 값이 실리지 않습니다. 그래서 이벤트에서도 빠지는 것이고(=V5 의 증상), 대신 306 bytes 로 끝납니다. FULL 은 변경 전 행을 남기기 위해 그 값을 TOAST 에서 꺼내(detoast) 통째로 WAL 에 넣습니다. 즉 V5 의 증상과 V5 의 비용은 같은 동전의 양면입니다 — 값을 안 실었기 때문에 못 읽었고, 읽히게 하려면 실어야 합니다.

    수치에 섞인 것

    좁은 표 UPDATE 의 총량 1.6~1.8 MiB 중 full page image 가 57개(약 456 KiB) 포함돼 있습니다. FPI 는 두 설정에 같은 수로 들어가므로 증가율 판정에는 영향이 없고, 절대값을 다른 환경과 비교할 때만 감안하면 됩니다. 유휴 바닥값은 이번 회차 0 B 였습니다.

    06테이블별 판단 — 내리면 무엇을 잃는가

    후보 컬럼이 없다는 것만으로 FULL 을 내릴 수는 없습니다. before 이미지를 다른 기능이 쓰고 있을 수 있기 때문입니다. 코드를 읽어 짐작하는 대신 파이프라인에 흘려서 확인했습니다.

    표TOAST 후보before 를 쓰는 곳DEFAULT 실측판단
    car 없음 감사 로그 — 필드 단위 변경 식별 (V1) identifiable = false FULL 유지 — V5 가 아니라 V1 이 요구한다
    computer 없음 소프트 삭제의 PK 만 (DEFAULT 도 PK 는 싣는다) INSERT·UPDATE·소프트 삭제 모두 정상 DEFAULT 로 내려도 지금 기능은 유지된다
    grade · member 없음 computer 와 같은 형태 미측정 (computer 와 동일 구현) computer 와 같은 판단이 적용된다

    이번 회차에서 나온 가장 중요한 한 가지

    car 의 FULL 을 붙잡고 있는 것은 V5 가 아니라 V1 입니다. car 를 DEFAULT 로 내리자 감사 로그가 identifiable = false 로 남았습니다 — "안 바뀌었다"가 아니라 "판정을 못 했다"입니다. FULL 로 되돌리자 같은 UPDATE 가 changed_fields = price,updated_at 로 남았습니다.

    즉 REPLICA IDENTITY 는 V5 단독 결정이 아니라 V1(감사) · V5(TOAST) · V2(디스크) 세 항목의 교집합에서 정해집니다.

    ADR · 전 테이블 FULL 을 유지하되, 후보가 생기는 순간 재검토한다

    배경
    지금 캡처 대상에는 TOAST 후보 컬럼이 없고, 좁은 표에서 FULL 의 대가는 UPDATE 1.12배 · DELETE 1.22배로 크지 않다. 반면 감사 대상 테이블은 before 이미지가 필요해 내릴 수 없다.
    결정
    현 스키마에서는 전 테이블 FULL 을 유지한다. 절감폭(12~22%)이 테이블별로 설정을 갈라 관리하는 복잡도를 넘지 않는다.
    대가
    감사 대상이 아닌 세 표에 대해 12~22% 의 WAL 을 더 쓴다. V2 의 다운 허용시간이 그만큼 짧아진다.
    재검토 조건
    (1) 캡처 대상에 TOAST 후보 컬럼이 생겼을 때 — 그 표의 FULL 은 UPDATE 당 656배가 된다. (2) 감사 대상 테이블 목록이 바뀌었을 때. (3) V2 의 max_slot_wal_keep_size 상한을 확정해 WAL 여유가 제약이 됐을 때.
    실행 장치
    스키마 변경 절차에 scripts/toast-candidates.sql 실행을 넣는다. 조건 (1)을 사람이 기억으로 감시하면 놓친다.

    07부수 발견 — V2 의 165 bytes/변경 해석 교정

    시나리오 문서는 V2 의 165 bytes/변경 에 "REPLICA IDENTITY FULL 기준인 점 주의"라는 단서를 달고, V5 요구가 V2 디스크 압력을 키우고 있는 구조라고 적었습니다. 이번 측정은 그 절반을 교정합니다.

    문서의 서술측정 결과교정
    165 bytes/변경 은 REPLICA IDENTITY FULL 기준인 점 주의 INSERT 부하에서 DEFAULT 166 B / FULL 166 B — 차이 없음 V2 의 수치는 INSERT 1,000건으로 잰 값이라 REPLICA IDENTITY 와 무관하다. "FULL 기준이라 부풀려져 있다"는 단서는 불필요하다
    V5 요구가 V2 디스크 압력을 키우고 있는 구조 좁은 표 UPDATE 1.12배 / DELETE 1.22배, 넓은 표 UPDATE 656배 맞다. 다만 조건부다 — UPDATE/DELETE 부하에서만, 그리고 대용량 컬럼이 있을 때 폭발한다

    그래서 V2 의 다운 허용시간 산출은 부하 구성에 달려 있다

    같은 건수라도 INSERT 위주면 REPLICA IDENTITY 가 영향을 주지 않고, UPDATE/DELETE 위주면 FULL 이 12~22% 를 더 씁니다. V2 가 다운 허용시간을 산출할 때 쓰는 "변경 1건당 WAL" 은 연산 구성별로 다른 값이어야 합니다 — 단일 상수로 두면 UPDATE 가 많은 시간대에 허용시간을 과대평가하게 됩니다.

    08남은 판단과 조치

    검증과 측정은 끝났습니다. 남은 것은 절차와 업무 판단입니다. 항목을 클릭하면 체크 상태가 브라우저에 저장됩니다.

    V5 안에서 남은 판단 0 / 0

    • 선별 질의를 스키마 변경 절차에 넣기 (필수 · 실행 장치)후보 컬럼이 생기는 순간 그 표의 FULL 은 UPDATE 당 656배가 된다. 사람이 기억으로 감시하면 놓친다
    • 실제 대상 테이블에 선별 질의 1회 실행지금 결과는 PoC 스키마 기준이다. 실제 업무 테이블에는 대용량 컬럼이 있을 수 있다
    • 감사 대상이 아닌 표의 REPLICA IDENTITY 를 내릴지 결정절감 12~22%. 설정을 표별로 가르는 관리 복잡도와 견줄 것 (06 절 ADR 은 유지 쪽을 권한다)
    • 대용량 컬럼을 캡처 대상에 넣을지 결정넣으면 FULL 은 사실상 불가능하고, DEFAULT 면 그 컬럼은 이벤트로 동기화할 수 없어 원본 재조회가 필요하다
    • V2 의 "변경 1건당 WAL" 을 연산별로 나눌지 (V2 와 공동)단일 상수는 UPDATE 가 많은 시간대에 다운 허용시간을 과대평가한다
    • 계측 산출물을 저장소에 남기기 (전 시나리오 공통)results.md 가 build/ 아래라 gitignore 에 걸린다. 보고서의 실행 시점 수치를 나중에 대조할 원본이 남지 않는다 — 10 절 참조

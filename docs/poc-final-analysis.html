V3

캡처 연결고리 끊김 — 조용히 넘어가지 않는다

측정값읽는 법
슬롯 강제 삭제 후 재기동끊긴 100건 중 0건 수신가드(SlotContinuityGuard)가 오프셋 LSN 과 슬롯을 대조해 기동을 거부하고 지표·경보·로그로 알린다
간접 탐지의 한계up{job="cdc-service"} = 1앱은 살아서 스크랩에 응답한다. "스크랩 실패 = 문제" 감시로는 이 상황을 못 잡는다 — 앱이 직접 내는 cdc_capture_gap 이 필요한 이유

복구 절차에서 실제로 빠져 있던 단계

첫 복구 시도는 실패했습니다 — 오프셋 파일만 지우고 재기동했더니 가드가 계속 거부했습니다. 가드가 보는 것은 파일이 아니라 수신측 cdc_checkpoint 표이기 때문입니다. 절차는 5단계로 확정했습니다: 정지 → 재적재 → 삭제 대사 → 체크포인트·오프셋 초기화 → 재기동. 하나만 빠져도 정합이 안 맞거나 파이프라인이 아예 안 뜹니다. 이중화는 측정이 아니라 이미 정해진 결과입니다 — PostgreSQL 16 은 슬롯을 standby 로 동기화하지 않으므로 페일오버 = 재동기화이고, 승계(sync_replication_slots)는 17부터라 버전 선택이 곧 대응책입니다.

재기동 직후의 중복(같은 LSN 200건 재유입)은 전 표에서 이중 반영 0으로 차단됩니다. 문제는 두 번째 중복 경로인 DLQ 재처리입니다 — 격리 → 원인 수정 → 그 사이 정상 갱신 → 재처리 순서에서는 중복이 아니라 역전이 위험이고, 이를 막는 힘은 표마다 다릅니다.

부수 발견 — DLQ 상태만으로는 구분이 안 된다

DLQ 는 재처리 결과를 예외 유무로만 판정합니다. 가드에 막혀 0행이 반영돼도 RESOLVED 가 되므로 네 표가 모두 RESOLVED 였지만 실제로 값이 바뀐 것은 car 하나였습니다. "반영됨"과 "차단됨"을 상태로 나눌지(SUPERSEDED)는 남은 판단입니다.

02설계로만 풀리는 한계 세 가지

설정이나 코드로 우회할 수 없습니다. 스키마나 버전을 바꾸거나, 받아들이고 절차로 감싸야 합니다.

한계왜 우회가 안 되는가선택지
페일오버 시 슬롯 소실 (V3) PostgreSQL 16 은 논리 복제 슬롯을 standby 로 동기화하지 않는다. 승계는 17의 sync_replication_slots 부터 버전 선택이 곧 대응책. 16 이면 페일오버 = 재동기화로 못박고 소요(10만 행 40.2초 실측)를 근거로 둔다
변환 표의 값 대사 불가 (V6) computer 는 brand+model → full_name 변환이 걸려 견줄 체크섬 대상이 없다 건수 대사만으로 가거나, 수신에 변환 전 값 또는 원천 시각을 실어 대사를 살린다
가드 없는 표의 재처리 위험 (V4) car 는 수신 스키마가 원천과 같아 source_lsn 이 없다 — 비교할 값이 없으니 조건절도 없다 컬럼 추가(스키마 동일성 포기) / 재처리 대상 제외 / 절차로 차단 중 택일

03가장 큰 위험 — 오류를 남기지 않는 실패

V4 의 car 회귀는 파이프라인 어디에도 오류를 남기지 않습니다. 적재는 성공(1행 갱신)하고 DLQ 는 RESOLVED 가 되며 지표도 정상입니다. 알려주는 신호는 체크섬 대사의 불일치 하나뿐이고, 그것도 대사 주기가 돌아온 뒤입니다.

그 체크섬 대사가 지금 경보 밖에 있다

건수 대사와 고아 참조는 exporter 가 상시로 내고 경보 22건에 연결돼 있지만, 체크섬 대사는 경보 어디에도 없습니다 — 스크립트로만 돕니다. 값이 조용히 어긋나는 두 경우(V4 의 car 회귀, V6 의 구간 밖 변조)를 잡는 유일한 그물이 사람이 돌려야만 도는 상태입니다. "조용한 어긋남을 누가 언제 잡는가"가 이 구조의 실질적인 안전선이고, 선행 결정 4건 중 하나(체크섬 대사 실행 주체)가 정확히 이 빈자리를 가리킵니다.

04하나의 값이 세 갈래를 정한다 — max_slot_wal_keep_size

남은 결정을 하나씩 떼어 정하면 서로 어긋납니다. 이 값 하나가 세 항목을 동시에 정합니다.

V2 · 다운 허용시간

-1 이면 "디스크 찰 때까지"(10,000 변경/s 에서 5.2일), 상한을 걸면 그 크기만큼으로 짧아진다 (1 GB 면 8분)

V3 · 무효화 경계

상한 초과 순간 슬롯이 무효화되어 재동기화로 넘어간다. unreserved 경고 단계의 대응 시간도 이 값이 정한다

V4 · 복구 가능한 최대 폭

중복으로 되감을 수 있는 WAL 폭이 곧 이 상한이다. 되감기 여유와 디스크 안전은 같은 값의 양면

고를 것은 시간이 아니라 실패 방식

상한 없음(-1)은 "슬롯은 절대 안 잃지만 최악에 source DB 가 먼저 멈춘다", 상한 설정은 "원천은 절대 안 죽지만 초과 순간 재동기화를 감수한다"입니다. 권고는 디스크 여유의 20~30% 상한 + 재동기화 절차 준비(V3 에서 검증 완료)이며, 값을 확정하려면 운영 변경 속도 실측이 선행입니다.

시나리오 문서가 제시한 권고에 현재 상태와 검증 근거를 붙였습니다.

06Debezium 자체 결함 — 판단 기준과 대안

"재현 시 판단"으로만 있던 항목에 기준을 고정했습니다. 기준이 없으면 장애 한 번에 전환 논의가 됩니다.

항목판정 기준
재현 요건같은 시나리오 3회 이상 + 최신 패치 버전에서도 재현 + 업스트림 이슈 확인
행업(hang)엔진 스레드는 살아 있는데 이벤트 0건 · 슬롯 10분 이상 정지 — CdcSlotNotAdvancing 과 cdc_events_total 정체 동시
오프셋 오염재기동 시 저장 LSN 이 슬롯 restart_lsn 보다 뒤 — 가드 로그가 그대로 근거
메모리 누수24시간 부하에서 GC 이후에도 heap 단조 증가

대안 두 개는 등가가 아니다

버전 컬럼 폴링은 DELETE 를 못 잡습니다 — 원본이 소프트 삭제를 쓴다는 전제가 필요합니다. 논리 복제 직접 소비(pgjdbc)는 슬롯·오프셋·스키마 변경 처리를 직접 만들어야 하므로 V2~V4 에서 검증한 것을 다시 만드는 셈입니다. 따라서 전환 판단의 첫 질문은 "Debezium 이 불안정한가"가 아니라 "원본 테이블에 소프트 삭제를 강제할 수 있는가"입니다. 안 되면 선택지가 사실상 하나입니다.

07결정 요청 — 전환 전 선행 4건

결정정하지 않으면
1. max_slot_wal_keep_size 상한 — 디스크 고갈이냐 재동기화냐허용시간이 "디스크 찰 때까지"로 남고, V2·V3·V4 세 항목이 따로 놀게 된다
2. car 계열 표의 순서 가드 — source_lsn 추가 / 재처리 제외 / 절차 차단DLQ 재처리를 운영 수순에 넣을 수 없다 — 조용한 회귀 경로가 열려 있다
3. PostgreSQL 버전 — 16(페일오버 = 재동기화) vs 17(슬롯 승계)이중화 설계를 확정할 수 없다
4. 체크섬 대사 실행 주체 — 배치 잡인지 exporter 인지조용한 어긋남을 잡는 유일한 그물이 경보 밖에 남는다

그다음에 정할 것

구간 대사 주기·폭, 전체 대사 야간 시각최대 탐지 지연 = 야간 배치 주기. 구간 폭은 야간 주기보다 넉넉해야 그물 사이에 구멍이 없다
감사 로그 보관 정책243만 행에서 처리량 1,177/s → 283/s. 정책 없이는 어떤 표에도 켜지 않는다
대용량 컬럼 캡처 여부 / 변환 표 값 대사 범위둘 다 수신 스키마를 바꾸느냐의 문제 (V5 · V6)
1만 건 버스트의 실존 여부 확인존재하면 예산 상향 / 배치 분할 / 적재 개선 중 택일 (V1)

추가로 재야 할 것

운영 변경 속도 실측허용시간 표의 어느 행을 볼지, 상한값·경보 임계를 정하는 전제
standby 를 세운 실제 페일오버 전환 실측슬롯 소실 복구는 40.2초(10만 행)로 실측됐고, 전환(승격 포함) 전체만 남았다
실제 업무 테이블에 점검 질의 1회toast-candidates.sql · reconcile.sql. 지금 결과는 PoC 스키마 기준이다

CDC 장애 복구 보고서

v1.0 · 2026-09-02 · embedded-cdc-go

    Incident Report & Countermeasures

    cdc-service 크래시 루프 70분 — 장애 복구와 대처 방안

    2026-09-02, Go 스택(embedded-cdc-go)의 cdc-service 가 984회 재시작을 반복하며 70분간 캡처를 멈췄습니다. 데이터 유실은 없었으나, 가드가 정상 상태를 유실로 오판했고 그 사실을 밖으로 알리는 지표가 하나도 없었습니다. 이 문서는 무엇이 일어났는지, 어떻게 복구했는지, 재발을 막기 위해 무엇을 만들지를 정의합니다.

    복구 완료 13:20 KST 데이터 유실 0건 근본 원인 미조치 Go 관측 지표 부재 commit 4212425

    00범위와 전제

    이 장애는 세 개의 원인이 사슬로 엮여 있습니다. 어디까지를 이번에 끊을지 먼저 못 박습니다.

    이번에 조치하는 것

    • 가드 판정식 교정 — 체크포인트 대신 커넥터 확인 위치를 비교
    • 정지 시 프로세스를 죽이지 않고 신호를 내보내는 구조
    • Go 스택 관측 지표·경보 파리티 (Java 기준)
    • 라이브러리 패닉을 프로세스 종료로 번지지 않게 차단

    이번에 하지 않는 것

    • go-pq-cdc 포크·패치 — 상류 이슈로 올리고 회피책으로 대응
    • 수신 적재 처리량 최적화 — 별도 과제(7번 병목)로 분리
    • 실제 Primary/Standby failover 검증 — 단일 인스턴스 PoC 범위 밖
    • Java 스택 재작업 — 이미 동일 대책이 반영돼 있음

    전제

    이 장애의 방아쇠였던 wal_sender_timeout 은 이미 60초에서 5분으로 올려 둔 상태였습니다. 빈도는 9회에서 1회로 줄었지만 없어지지 않았습니다. 즉 타임아웃 상향은 완화책이지 해결책이 아니며, 이번 대책의 전제는 "타임아웃은 다시 발생한다" 입니다.

    01장애 시나리오

    실측 로그로 확정된 인과 사슬입니다. 각 ID 는 이후 대책·검증 절에서 그대로 참조합니다.

    발생 경로

    SC-01 · 적재 부하 중 walsender 가 끊기고 프로세스가 패닉으로 죽는다

    Given
    source 에 대량 적재가 진행 중이고, 파이프라인이 수신 적재로 backlog 를 소화하고 있다
    When
    수신 적재가 wal_sender_timeout(5분) 을 넘도록 리스너를 붙잡아 standby status update 가 나가지 못한다
    Then
    PostgreSQL 이 walsender 를 종료하고1, go-pq-cdc 가 panic("corrupted connection") 으로 프로세스를 죽인다2

    SC-02 · 재기동 시 가드가 정상 상태를 유실로 오판한다

    Given
    슬롯의 restart_lsn = 0/B358B288, cdc_checkpoint.last_applied_lsn = 0/B33A5CC0
    When
    기동 시 SlotContinuityGuard.DetectGap() 이 restartLSN > lastApplied 를 평가한다3
    Then
    1,988,040 bytes 갭으로 판정해 기동을 거부한다. 그러나 그 구간은 이미 적용된 뒤였고 실제 유실은 0건이었다

    SC-03 · 멈춘 사실이 밖으로 나가지 않는다

    Given
    compose 의 재시작 정책이 restart: unless-stopped 이다
    When
    가드가 기동을 거부하고 프로세스가 종료된다 — 이것이 984회 반복된다
    Then
    Go 스택에는 cdc_capture_gap 도 경보 규칙 파일도 없어 대시보드에 아무 신호가 남지 않는다. 70분간 아무도 알지 못했다

    복구 경로

    SC-04 · 갭을 감수하고 재개해 backlog 를 소화한다

    Given
    체크섬 대조로 실제 유실이 없음을 확인했고, 슬롯이 710MB 를 아직 들고 있다
    When
    CDC_FAIL_ON_CAPTURE_GAP=false 로 일회성 기동한다
    Then
    16분 만에 backlog 를 소화하고 source·target 이 551만 행 기준 체크섬까지 일치한다

    02무엇이 어긋났는가

    박스를 끌어 배치를 바꿀 수 있습니다. 구조가 바뀌면 JSON 버튼으로 내보내 이 파일의 dgm-data 블록에 붙여넣습니다.

    진행 지점이 세 곳이고, 가드는 잘못된 두 곳을 비교했다

    오판의 구조

    슬롯은 heartbeat 와 라이브러리 자체 ack 두 경로로 전진합니다. 둘 다 우리 적용 파이프라인을 거치지 않습니다. 반면 cdc_checkpoint 는 배치를 적용한 뒤에만 갱신됩니다. 따라서 아무 것도 잃지 않아도 restart_lsn 이 last_applied_lsn 을 앞지르는 것이 정상입니다. 가드는 이 둘을 비교하고 있어 구조적으로 오탐합니다.

    04복구 방식 비교와 선택

    발견 시점에 선택지는 셋이었고, 되돌릴 수 없는 결정이라 근거를 남깁니다.

    안방식장점단점적합도
    A. 재동기화 down -v 후 전량 재적재 상태가 확실하게 깨끗해진다 551만 행 × 3테이블 재적재. 30분 이상 소요되고 PoC 측정 이력이 초기화된다 과잉
    B. 갭 감수 재개선택 CDC_FAIL_ON_CAPTURE_GAP=false 일회성 기동 슬롯이 보유한 710MB 를 그대로 살린다. 16분에 완료 실제 유실이 있었다면 그대로 확정된다 — 사전 검증이 필수 적합
    C. 체크포인트 수동 전진 cdc_checkpoint 를 슬롯 위치로 UPDATE 설정 변경 없이 가드를 통과시킨다 운영 DB 직접 수정. 판단 근거가 코드·설정 어디에도 남지 않는다 부적합

    ADR-01 · 갭을 감수하고 재개한다 (B안)

    배경
    가드가 1,988,040 bytes 유실을 주장했으나, 행 수·체크섬·키 연속성 대조로 실제 유실이 없음을 먼저 확인했습니다. 슬롯은 710MB 를 아직 보유하고 있었습니다.
    결정
    CDC_FAIL_ON_CAPTURE_GAP 을 compose 환경변수로 노출하되 기본값은 true 로 두고, 셸에서 한 번만 덮어써 기동했습니다. 레포에는 안전한 기본값이, 명령 이력에는 사람의 판단이 남습니다.
    대가
    이 스위치가 존재한다는 사실 자체가 오용 경로입니다. 상시 false 로 운영하면 조용히 틀린 데이터가 흘러갑니다. 그래서 절 09 에 복귀 절차를 못 박았습니다.
    재검토
    가드 판정식이 W1 로 교정되면 이 스위치의 사용 빈도가 0 이 되어야 합니다. 교정 후 30일 내에 한 번이라도 다시 쓰였다면 판정식이 여전히 틀린 것이므로 ADR-01 을 재검토합니다.
    실제 복구 명령 · 2026-09-02 13:04
    # 1) 유실 여부를 먼저 확정한다 — 이 단계 없이 2)로 가면 안 된다

  "select md5(string_agg(id||'|'||name||'|'||brand||'|'||price, ',' order by id)) from car"
podman exec emb-cdc-go-target-pg psql -U postgres -d targetdb -Atc \
  "select md5(string_agg(id||'|'||name||'|'||brand||'|'||price, ',' order by id)) from car"

# 2) 갭을 감수하고 일회성 기동 — 기본값은 건드리지 않는다
CDC_FAIL_ON_CAPTURE_GAP=false podman compose -f docker-compose.yml up -d cdc-service

# 3) backlog 소화 확인
podman exec emb-cdc-go-source-pg psql -U postgres -d sourcedb -Atc \
  "select pg_size_pretty(pg_current_wal_lsn()-confirmed_flush_lsn) from pg_replication_slots"

    06고려사항과 착수 전 합의

    상황그대로 두면 생기는 일대응

    테스트가 새는 지점

    시간 — 감쇠 창(rollingMax)과 heartbeat 나이는 time.Now() 를 직접 부르면 테스트가 흔들립니다. Clock 인터페이스를 주입해 고정 시각으로 검증하십시오.
    LSN — 랜덤 값으로 테스트하면 경계(같은 값, 1 차이)를 놓칩니다. 실제 장애의 값 0xB358B288 / 0xB33A5CC0 를 상수로 박아 회귀 테스트로 남기십시오.
    공유 DB 상태 — verify.sh 는 운영 테이블과 슬롯을 건드리지 않고 verify_* 전용 자원만 씁니다. 이 규칙을 깨면 부하 테스트와 서로 오염됩니다.

    성공 판정 기준

    교정 전(현재) — 4번을 실행하면 캡처 연결고리 유실 이 로그에 남고 재시작 횟수가 계속 오릅니다. 이것이 재현 성공입니다.
    교정 후(W1 적용) — 4번을 실행해도 재시작 횟수가 0 이고 스트림이 이어집니다. 반면 SELECT pg_drop_replication_slot('embedded_cdc_go_slot') 후 재기동하면 여전히 갭으로 판정되어야 합니다. 둘 다 만족해야 통과입니다.

    자주 나는 오류

    포트 충돌 — Java 스택(56xxx)과 Go 스택(57xxx)은 포트·컨테이너 이름이 전부 달라 나란히 뜹니다. 같은 스택을 두 번 올리면 container name already in use 가 납니다.
    볼륨 잔존 — down 만 하면 슬롯과 데이터가 남아 다음 기동에서 예상치 못한 갭 판정이 납니다. 재현 실험 사이에는 down -v 를 쓰십시오.
    하위 compose 단독 기동 — infra/db/*.yml 등을 -f 로 따로 올리면 프로젝트가 갈려 같은 container_name 을 두고 충돌합니다. 루트 docker-compose.yml 하나만 씁니다.

    10복귀와 롤백

    복구 스위치 원복backlog 소화가 끝나면 CDC_FAIL_ON_CAPTURE_GAP 없이 재기동해 기본값 true 로 되돌립니다. 이것을 빠뜨리면 다음 진짜 유실이 조용히 통과합니다.
    W1 그림자 검증교정된 판정식을 로그로만 출력하는 모드로 먼저 배포해, 기존 판정과 새 판정이 갈리는 지점을 1주간 수집합니다.
    전환새 판정식을 기동 거부 근거로 승격합니다. 동시에 W2 의 신호(cdc_capture_gap)가 나가는지 확인합니다.
    정리기존 판정식과 CdcCaptureGapByLsn 경보를 제거할지 결정합니다. 앱이 아예 안 뜨는 상황의 대체 경로가 필요하면 남깁니다.

    롤백 기준

    W1 — 그림자 검증 1주 동안 진양성을 한 건도 잡지 못하면 전환하지 않습니다. 오탐만 없애고 탐지력을 잃은 것일 수 있습니다. 되돌리려면 판정식을 restartLSN > lastApplied 로 복원합니다 — 지표와 테스트는 그대로 둬도 동작에 영향이 없습니다.
    W2 — 프로세스를 살리는 쪽의 위험은 "죽어야 할 때 안 죽는 것" 입니다. cdc_capture_gap == 1 경보가 5분 내 울리지 않는 것이 한 번이라도 관측되면 즉시 종료 방식으로 되돌립니다.
    W3 — recover() 후 스트림 재연결이 3회 연속 실패하면 recover 를 포기하고 프로세스를 종료합니다. 무한 재연결이 더 위험합니다.

    Java 스택과의 차이 — 왜 같은 장애가 없었는가

    같은 부하(누적 360만 이벤트)에서 Java 스택은 walsender 종료 0회, 재시작 0회였습니다. 구조적 차이는 셋입니다. (1) keepalive 를 이벤트 처리와 별도 스레드로 보내므로 적재가 밀려도 응답이 끊기지 않습니다. (2) 오프셋을 커넥터가 파일로 직접 관리해 "어디까지 읽었는가" 가 적용 파이프라인과 분리돼 있습니다. (3) 갭 발견 시 프로세스를 죽이지 않고 cdc_capture_gap 과 health DOWN 으로 신호를 냅니다. W1~W3 은 이 셋을 Go 쪽에 맞추는 작업입니다.

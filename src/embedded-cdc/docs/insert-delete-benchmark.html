    Measurement Report

    INSERT · DELETE 배치별 CDC 반영 시간

    테이블당 100행부터 300,000행까지 여섯 단계를 순차로 넣고 지우며, Debezium Embedded(Java)와 go-pq-cdc(Go) 두 스택이 target DB에 반영을 끝내기까지 걸린 시간을 쟀습니다. 앞 배치가 완전히 반영된 뒤에만 다음 배치를 넣었습니다.

    측정 2026-09-02 17:02~17:18 배치 6종 × 2연산 × 스택 2종 완료 판정은 target DB 직접 폴링 전 구간 정합성 일치

    00측정 범위와 전제

    두 스택을 완전히 새로 올린 상태에서 시작했습니다. 앞선 측정의 잔여 데이터는 남아 있지 않습니다.

    측정한 것

    • source에서 INSERT · DELETE를 실행한 시간
    • 커밋 완료부터 target 3개 테이블 반영 완료까지의 시간
    • 구간 평균 처리량 (행/초)
    • cdc-service 컨테이너의 CPU · 메모리 최대치

    측정하지 않은 것

    • UPDATE — 별도 측정이 필요합니다 (07절 참고)
    • 두 스택 동시 부하의 상호 간섭 (source DB가 서로 분리되어 있음)
    • 재기동·장애 상황에서의 복구 시간

    전제

    두 스택은 컨테이너 · 포트 · 네트워크 · 복제 슬롯이 모두 분리되어 있고 source DB도 각각 따로 띄웁니다. 같은 SQL을 두 source DB에 각각 실행했으므로 source 실행 시간은 스택별로 다른 값입니다. 측정은 초기 시드(car 3 / computer 3 / member 5)만 있는 상태에서 시작해, INSERT 사다리로 611,100행을 쌓고 DELETE 사다리로 같은 양을 되돌렸습니다.3

    01측정 방법

    앞선 측정에서 배치가 겹쳐 값이 섞인 적이 있어, 이번에는 완료 확인을 스크립트가 강제합니다.

    구간판정 기준이유
    source 실행psql \timing 합계 (3개 문장) DB가 쓰기를 끝내고 커밋할 때까지. CDC와 무관한 순수 원천 비용입니다.
    반영 완료target의 살아있는 행 수 = source 행 수 car는 물리 삭제라 전체를, computer·member는 소프트 삭제라 deleted = false만 셉니다.
    폴링 간격0.3초 Prometheus는 5초 간격이라 100건 배치가 해상도 아래로 묻힙니다. target DB를 직접 봅니다.
    배치 순서앞 배치 반영 완료 후 다음 배치 CDC 스트림은 하나라 겹치면 뒤 배치가 앞 배치 뒤에 줄을 섭니다. 그러면 "이 배치의 시간"이 아니게 됩니다.
    측정 대상 SQL — 세 스택 공통
    # INSERT — 테이블당 cnt 행 (member / car / computer)
psql -v ON_ERROR_STOP=1 -v cnt=300000 -f - < scripts/seed-bulk.sql

# DELETE — id 가 가장 작은 행부터 cnt 개씩
psql -v ON_ERROR_STOP=1 -v cnt=300000 -f - < scripts/delete-bulk.sql

    DELETE 대상 선정에 ORDER BY random()을 쓰지 않습니다. 수백만 행에서 매번 풀스캔과 정렬이 되어, 재려는 CDC가 아니라 부하 생성 쪽에서 시간을 먹기 때문입니다. PK 인덱스를 따라 앞에서부터 cnt개만 훑습니다.4

    source는 6배 싸지만 CDC는 그대로입니다

    30만행 기준 source 실행이 INSERT 6,565ms → DELETE 1,107ms로 6분의 1입니다. 값을 만들어 넣는 것보다 PK로 지우는 것이 훨씬 싸기 때문입니다. 그런데 CDC 반영은 213.5초 → 212.1초로 거의 차이가 없습니다. 파이프라인 비용은 연산 종류가 아니라 이벤트 개수가 정한다는 뜻입니다.

    메모리 차이가 20배입니다

    Java는 전 구간 700~900MB로 평평합니다(JVM 힙 상한에 눌린 모습). Go는 대부분 40~72MB로, 같은 일을 20분의 1 메모리로 합니다. 다만 INSERT 30만행 구간에서 Go가 648MB까지 한 번 치솟습니다 — 밀린 이벤트를 안에 들고 있을 때 나타나는 특성으로, 배치가 더 커지면 계속 오릅니다. 컨테이너에 메모리 상한을 걸지 않은 상태이므로 대량 적재 전에는 상한을 정해야 합니다.

    06정합성

    시간보다 먼저 확인해야 하는 값입니다. 틀린 결과를 빨리 만드는 것은 의미가 없습니다.

    스택source (car/computer/member)target 살아있는 행target 소프트 삭제
    Java3 / 3 / 53 / 3 / 5611,100 / 611,100
    Go3 / 3 / 53 / 3 / 5611,100 / 611,100

    사다리를 다 돌고 나면 초기 시드만 남아야 합니다. 두 스택 모두 그렇게 끝났습니다. computer·member는 소프트 삭제라 지운 611,100행이 deleted = true로 남아 있고, car는 물리 삭제라 사라졌습니다. 12개 배치 전부에서 배치 직후 source와 target이 일치했습니다.

    소프트 삭제의 대가

    타깃 DB 크기가 Java 321MB · Go 319MB인데 소스는 264MB입니다. 지운 행을 계속 들고 있기 때문입니다. 늦게 도착한 갱신이 지워진 행을 되살리는 것을 막으려는 설계인데, 그 대가가 이 차이입니다.

    07이 측정의 한계

    숫자를 인용하기 전에 읽어야 하는 부분입니다.

    한계영향대응
    1회 측정같은 배치를 반복하지 않아 편차를 알 수 없음결론을 낼 배치는 3회 반복 후 중앙값 사용
    작은 배치는 고정 지연이 지배100·1,000행 값(약 2.2~2.6초)은 처리 능력이 아님처리량 비교는 10,000행 이상만 인용
    UPDATE는 빠져 있음UPDATE는 REPLICA IDENTITY FULL 때문에 변경 전 이미지까지 실려 성격이 다름별도 사다리로 측정 필요
    Java 스택의 감사 기록이 켜져 있음CDC_AUDIT_CHANGED_FIELDS=car. 다만 UPDATE에만 걸리므로 이번 결과에는 영향 없음6UPDATE 측정 시에는 반드시 끄고 조건을 맞출 것
    단일 호스트 · 컨테이너 환경두 스택과 DB 4개가 CPU · 디스크를 공유절대 성능치가 아니라 상대 비교용으로만 사용
    Go 메모리 상한 미설정30만행에서 648MB까지 오른 뒤 어디까지 오르는지 미확인다음 측정은 mem_limit을 걸고 수행

    08재현 절차

    같은 숫자를 다시 뽑는 순서입니다.

    1. 두 스택 기동 (각 스택 루트에서)
    cd src/embedded-cdc     && docker compose up -d --build
cd src/embedded-cdc-go  && docker compose up -d --build
    2. 사다리 실행 — 앞 배치 완료 후 다음 배치
    # 배치마다 두 소스에 같은 cnt 로 넣고, 두 타깃이 모두 따라잡을 때까지 기다린다
for CNT in 100 1000 10000 100000 200000 300000; do
  podman exec -i emb-cdc-source-pg    psql -U postgres -d sourcedb \
      -v ON_ERROR_STOP=1 -v cnt=$CNT -f - < src/embedded-cdc/scripts/seed-bulk.sql
  podman exec -i emb-cdc-go-source-pg psql -U postgres -d sourcedb \
      -v ON_ERROR_STOP=1 -v cnt=$CNT -f - < src/embedded-cdc-go/scripts/seed-bulk.sql
  # target 의 살아있는 행 수가 source 와 같아질 때까지 0.3초 간격 폴링
done
    3. 정합성 확인 — 세 스택 공통
    # source
SELECT (SELECT count(*) FROM car), (SELECT count(*) FROM computer), (SELECT count(*) FROM member);
# target — computer/member 는 소프트 삭제라 살아있는 행만 센다
SELECT (SELECT count(*) FROM car),
       (SELECT count(*) FROM computer WHERE NOT deleted),
       (SELECT count(*) FROM member   WHERE NOT deleted);

    재측정 시 확인할 것 0 / 0

    • 직전 배치의 반영이 완전히 끝난 뒤 다음 배치를 넣는다겹치면 뒤 배치가 앞 배치 뒤에 줄을 서 "이 배치의 시간"이 아니게 된다
    • 두 source DB에 같은 cnt 값을 넣는다한쪽만 크면 비교가 성립하지 않는다
    • Java 감사 설정을 확인한다UPDATE 측정이라면 CDC_AUDIT_CHANGED_FIELDS 를 비워 조건을 맞춘다
    • 호스트에서 다른 무거운 작업을 돌리지 않는다두 스택이 같은 CPU · 디스크를 공유한다
    • Go 컨테이너 메모리 상한을 정한다30만행에서 648MB까지 올랐다. 더 큰 배치는 상한 없이 돌리지 않는다
    • 시드 데이터에 실제 개인정보를 넣지 않는다seed-bulk.sql 은 난수 조합 문자열만 생성한다

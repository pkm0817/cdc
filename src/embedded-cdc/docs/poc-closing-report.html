    Debezium Embedded CDC — 갈 수 있다, 다만 네 가지를 먼저 정해야 한다

    V1~V6 검증을 마치며 그래서 무엇을 할 것인가를 정리한 문서입니다. 수치와 항목별 근거는 「V1~V6 종합 근거」에 있고1, 이 문서는 그 결과가 어떤 결정을 요구하는지와 그 결정들이 서로 어떻게 얽혀 있는지만 다룹니다.

    기술 검증 통과 · 29/29 전환 전 선행 결정 4건 구조적 한계 3건 산출물 5문서 · 3시나리오 · 2스크립트

    00결론

    이 구조로 갈 수 있습니다. 통과 기준 여섯 개를 모두 충족했고, 유실 경로는 전부 막혀 있거나 탐지됩니다. 다만 "통과했다"가 "그대로 옮기면 된다"는 뜻은 아닙니다 — 검증 과정에서 드러난 것은 기술의 한계가 아니라 아직 정해지지 않은 선택이었습니다.

    기술 판정

    통과. Kafka 없이 애플리케이션 안에서 도는 구성으로 지연·유실·중복·대사 요구를 모두 만족합니다.

    전환 준비도

    미완. 코드가 아니라 수치와 스키마 결정 4건이 남아 있습니다.

    가장 큰 위험

    조용한 어긋남. 오류 없이 데이터만 과거로 돌아가는 경로가 하나 실재합니다.

    되돌릴 수 있는가

    예. 재동기화로 정합을 복원하는 절차가 검증됐습니다(101/101).

    한 문장으로

    이 PoC 가 남긴 가장 중요한 결과는 "된다"가 아니라 "무엇을 정해야 되는가"의 목록입니다. 그중 하나의 값(max_slot_wal_keep_size)이 세 항목을 동시에 결정하고 있어, 따로 정하면 서로 어긋납니다.

    01검증으로 확인된 것

    여섯 항목에서 하나씩. 수치의 출처는 전부 검증 스크립트 산출물입니다2.

    항목확인된 사실이것이 뜻하는 것
    V1 단건 지연 0.5초(예산 5초), 1만 건 버스트 6,218 events/s 무유실, 필드 단위 변경을 값까지 식별 지연은 여유가 크다. 다만 지연을 결정하는 것은 건수가 아니라 트랜잭션 크기다 — 버스트에서 예산에 가까워진다
    V2 다운 중 1,000건 → 재기동 후 1,000/1,000, 유실 0. 변경 1건당 WAL 165 bytes 슬롯이 붙잡아 주는 한 유실은 없다. 문제는 얼마나 오래 붙잡게 둘 것인가다
    V3 슬롯이 사라지면 엔진이 기동을 거부하고 가드가 탐지. 재동기화로 101/101 복원 조용히 어긋난 채 돌지 않는다. 복구 경로가 실재하고 검증됐다
    V4 중복 200건이 실제로 유입돼도 이중 반영 0. 단 car 는 DLQ 재처리에서 최신 값을 잃었다 중복을 막는 것은 파이프라인이 아니라 각 표의 UPSERT 문장이다. 그래서 표마다 답이 다르다
    V5 현 스키마에 TOAST 후보 컬럼 0개. FULL 비용은 좁은 표 12~22%, 대용량 컬럼이 있으면 656배 지금은 FULL 을 유지해도 싸다. 대용량 컬럼 하나가 추가되는 순간 비용 구조가 바뀐다
    V6 건수·체크섬 대사가 유실과 값 변조를 모두 검출. 격리된 부모는 대사를 통과하면서 고아를 남긴다 대사는 하나가 아니라 셋이 필요하다 — 건수, 체크섬, 고아 참조

    운영 관측도 살아 있다

    경보 규칙 22건이 로드돼 있고 각 항목의 판정 지표가 실제로 값을 냅니다 — cdc_capture_gap 0 · cdc_slot_status_code reserved · cdc_orphan_rows 0 · cdc_heartbeat_age_seconds 약 4초. 특히 cdc_guard_lsn_guard 는 V4 의 결론(car 0 / 나머지 1)을 대시보드에 그대로 보여 줍니다3.

    02설계로만 풀리는 한계 세 가지

    이 셋은 설정이나 코드로 우회할 수 없습니다. 스키마나 버전을 바꾸거나, 받아들이고 절차로 감싸야 합니다.

    한계왜 우회가 안 되는가선택지
    페일오버 시 슬롯 소실
    V3    		 PostgreSQL 16 은 논리 복제 슬롯을 standby 로 동기화하지 않는다. 승계해 주는 sync_replication_slots 는 17부터다 버전 선택이 곧 대응책이다. 16 을 쓴다면 페일오버 = 재동기화로 못박고 그 소요 시간을 미리 재둘 것
    변환 표의 값 대사 불가
    V6    		 computer 는 brand+model → full_name 변환이 걸려 양쪽 컬럼이 애초에 다르다. 체크섬을 견줄 대상이 없다 건수 대사만으로 가거나, 수신에 변환 전 값 또는 원천 시각을 함께 실어 대사 가능하게 만들 것
    가드 없는 표의 재처리 위험
    V4    		 car 는 수신 스키마가 원천과 같아 source_lsn 컬럼이 없다. 비교할 값이 없으니 조건절도 없다 컬럼을 추가하거나(스키마가 더 이상 "같지" 않게 됨), 그 표를 재처리 대상에서 빼거나, 절차로 막을 것

    가장 조심할 것 — 오류를 남기지 않는 실패

    V4 의 car 회귀는 파이프라인 어디에도 오류를 남기지 않습니다. 적재는 성공(1행 갱신)하고 DLQ 는 RESOLVED 가 되며 지표도 정상입니다. 알려주는 것은 체크섬 대사 하나뿐인데, 그 체크섬 대사가 지금 경보 22건 어디에도 없습니다 — 스크립트로만 돕니다.

    같은 모양의 실패가 V6 에도 있습니다 — 구간 밖에서 값만 바뀐 행은 구간 대사가 보지 못하고, 야간 전체 대사까지 기다려야 합니다. "조용한 어긋남을 누가 언제 잡는가"가 이 구조의 실질적인 안전선입니다.

    03결정들이 서로 얽혀 있다

    남은 결정을 하나씩 떼어 정하면 서로 어긋납니다. 특히 max_slot_wal_keep_size 한 값이 세 항목을 동시에 정합니다.

    하나의 값이 세 갈래로 갈라진다

    max_slot_wal_keep_size 를 -1(현재) 로 두면 다운 허용시간은 "디스크가 찰 때까지"이고 되감을 수 있는 폭도 그만큼 넓지만, 디스크 고갈 시 원천 DB 가 먼저 멈춥니다. 상한을 걸면 디스크는 안전해지지만 초과하는 순간 슬롯이 무효화되어 V3(재동기화)로 넘어갑니다.

    고를 것은 시간이 아니라 실패 방식입니다 — 디스크 고갈이냐, 슬롯을 버리고 재동기화냐. 디스크 여유 7.5 GiB 기준 실측값은 종합 근거 10절에 있습니다.

    04운영 전환 조건 — 순서대로

    앞의 것이 정해져야 뒤의 것을 정할 수 있습니다. 항목을 클릭하면 체크 상태가 브라우저에 저장됩니다.

    1
    실패 방식을 고른다
    max_slot_wal_keep_size 상한. 이 값이 V2 허용시간 · V3 무효화 경계 · V4 복구 폭을 동시에 정한다
    2
    스키마 결정을 내린다
    car 계열 순서 가드, 대용량 컬럼 캡처 여부, 변환 표의 대사 범위. 셋 다 수신 스키마를 바꾸느냐의 문제다
    3
    버전을 확정한다
    PostgreSQL 16 이면 페일오버 = 재동기화. 그 소요 시간을 실제 데이터 규모에서 재둔다
    4
    대사 운영 형태를 정한다
    구간 주기 · 구간 폭 · 야간 배치 시각. 체크섬 대사를 어디서 돌리고 어떻게 경보로 올릴지까지 포함
    5
    감사 로그 보관 정책을 붙인다
    243만 행에서 처리량이 1,177/s → 283/s 로 떨어졌다. 정책 없이 켜면 파이프라인이 스스로 느려진다
    6
    실제 스키마에 점검 질의를 돌린다
    toast-candidates.sql · reconcile.sql. 지금 결과는 PoC 스키마 기준이다

    전환 전 반드시 정할 것 0 / 0

    • car 계열 표에 source_lsn 을 둘 것인가두지 않으면 DLQ 재처리를 운영 수순에 넣을 수 없다. 두면 "원천과 같은 스키마"라는 성질을 잃는다
    • PostgreSQL 16 으로 갈 것인가16 이면 페일오버 시 슬롯이 사라진다. 17 이면 sync_replication_slots 로 승계된다
    • 체크섬 대사를 어디서 돌리고 어떻게 경보로 올릴 것인가지금은 스크립트뿐이라 경보 밖에 있다. 조용한 어긋남을 잡는 유일한 그물인데 사람이 돌려야만 돈다

    그다음에 정할 것 0 / 0

    • 구간 대사 주기·구간 폭, 전체 대사 야간 시각최대 탐지 지연 = 야간 배치 주기. 구간 폭은 야간 주기보다 넉넉해야 그물 사이에 구멍이 안 생긴다
    • 감사 로그 보관 정책 (파티셔닝 또는 보관 기간)정책 확정 전에는 어떤 표에도 감사를 켜지 않는다
    • 대용량 컬럼을 캡처 대상에 넣을 것인가넣으면 FULL 이 656배가 되고, DEFAULT 면 그 컬럼은 이벤트로 동기화할 수 없다
    • 변환 표(computer)의 값 대사를 포기할 것인가건수 대사만으로는 값이 틀어진 것을 못 잡는다
    • 스키마 변경 절차에 toast-candidates.sql 실행 넣기대용량 컬럼이 생기는 순간을 사람 기억으로 감시하면 놓친다

    추가로 재야 할 것 0 / 0

    • 다운 시간 2초/1분/10분 3점 측정 (WAL 선형성)지금은 2초 한 점뿐이라 허용시간을 외삽할 근거가 없다
    • 페일오버 후 재동기화 소요 시간·데이터량 실측PoC 규모(101행)의 값은 외삽에 쓸 수 없다
    • 실제 대상 테이블에 점검 질의 1회 실행지금 결과는 PoC 스키마 기준이다. 실제 업무 테이블에는 대용량 컬럼이 있을 수 있다

    05산출물

    문서만 남기지 않았습니다. 결론을 지키는 회귀 시나리오와 운영자가 그대로 돌리는 질의가 함께 있습니다.

    종류산출물역할
    문서 v1-v6-summary-report.html 시나리오 문서의 목차·항목을 그대로 두고 항목마다 근거를 채운 종합 문서
    v1~v6 회차별 보고서 (repo 최상위 docs/) 회차별 상세 — 무엇을 어떻게 재서 어떤 결론에 이르렀는지
    검증 시나리오 V4ReprocessGuardTest · V5ReplicaIdentityCostTest · V6ReconciliationScopeTest 이번 회차에 추가. 표별 가드 · FULL 비용 · 대사 사각지대를 매 실행마다 다시 확인한다
    기존 V1~V6 시나리오 합쳐서 29건. ./scripts/verify.sh 하나로 돈다
    운영 질의 scripts/toast-candidates.sql 관심 필드가 TOAST 에 걸리는지 판별하는 1단계 선별. 검증이 이 파일을 그대로 읽어 돌린다
    scripts/reconcile.sql 표별 전체·구간 대사를 한 번에. 어떤 표가 체크섬 대사까지 되는지도 함께 낸다
    관측 exporter 질의 · 대시보드 3 · 경보 규칙 22 각 항목의 판정을 상시 지표로. cdc_guard_lsn_guard 처럼 검증 결론이 그대로 지표가 된 것도 있다

    한 가지 원칙

    검증이 쓰는 질의와 운영자가 손으로 돌리는 질의를 같은 파일로 두었습니다. 따로 두면 조용히 갈라지고, 그러면 "검증에서 통과한 것"과 "실제로 쓰는 것"이 다른 것이 됩니다. 고아 참조 질의는 exporter YAML 에서, 대사와 TOAST 선별은 scripts/ 에서 읽습니다.

    06넘기기 전에 정리할 것

    결정과 별개로, 지금 상태 그대로 두면 오해를 부르는 것들입니다.

    항목지금 상태왜 정리해야 하는가
    검증 대시보드의 메모 패널 "V1~V6 13건 통과" 등 이번 회차 이전 상태로 멈춰 있음. V4·V5·V6 메모에 이번 결론(656배 · car 가드 없음 · 고아 대사 · 구간 한정)이 없음 대시보드 메모는 "보고서에 쓸 문장" 용도다. 문서와 갈라지면 어느 쪽이 맞는지 알 수 없다
    "다운 허용시간(추정)" 패널 유휴 구간 WAL 증가율로 계산되어 2.00 years 로 표시됨 야간 유휴에 보면 "2년 버틴다"로 읽힌다. 부하 가정을 명시하거나 고정 부하 기준으로 바꿔야 한다
    podman-exporter 스크레이프 타깃 down. docker 로 기동한 환경이라 쓰지 않는 타깃(rootless podman 스택용) 상시 down 인 타깃이 있으면 진짜 down 을 못 알아본다
    cdc_pipeline_halts_total 정지가 한 번도 없어 시계열이 아예 없음. 경보식이 increase() 라 동작에는 문제없음 패널이 0 이 아니라 "No data" 로 보인다. 정지 감시가 없는 것으로 오해할 여지가 있다
    DLQ 잔여 31건 (RESOLVED) 이번 검증 시나리오가 증거로 남긴 것. 운영 데이터가 아님 넘기기 전에 지우거나, 남기는 이유를 명시해야 다음 사람이 장애 흔적으로 오해하지 않는다

    이 중 하나는 성격이 다르다

    나머지는 표시의 문제지만, 대시보드 메모는 내용의 문제입니다. V4·V5·V6 회차에서 나온 결론 — 특히 car 가 되돌아간다와 FULL 이 656배가 될 수 있다 — 는 운영자가 대시보드만 보고는 알 수 없는 상태입니다.

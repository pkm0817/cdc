    검증 환경

    PostgreSQL 16.15 → Debezium Embedded 3.6.1 → PostgreSQL 16.15, Kafka 없음. java 스택 단독 기동(go · cdc-custom 스택은 내림). 스택을 새로 올린 상태에서 전 시나리오를 한 번에 돌린 결과입니다. 검증 전용 표(verify_*)와 전용 슬롯으로 도는 것이 원칙이며, V4-b · V5-b · V6-b 세 항목만 운영 표와 기동 중인 서비스를 그대로 씁니다 — 검증 대상이 각 표의 저장소 구현과 운영 재처리기 자체라서 복제본으로는 답이 나오지 않기 때문입니다.

    V1기본 캡처 기능 확인

    통과 기준 — 목표 지연 5초 이내 + 필드 단위 변경 식별 가능. 단건 지연은 예산의 10% 수준이고, 필드 단위 식별은 감사 로그 표로 남습니다.

    시나리오 문서의 항목상태근거
    목표 지연 N초 → 확정 반영 5초로 확정. 검증 코드(LATENCY_BUDGET) · 운영 경보(CdcLatencyBudgetExceeded) · 대시보드가 같은 값을 본다
    INSERT/UPDATE/DELETE 가 몇 초 안에 도착하는지 측정 왕복 지연 INSERT 500 ms · UPDATE 518 ms · DELETE 513 ms (예산 5초의 10%)
    UPDATE 에서 어떤 필드가 바뀌었는지 식별 가능한지 측정 바뀐 두 필드만 검출 — [amount, status], 값까지 판독(status: NEW → CONFIRMED, amount: 20000.00 → 22000.00). 안 건드린 필드는 변경으로 안 잡힘
    대량 변경 1만 건 배치에서 밀리지 않는 처리량 측정 6,218 events/s, 수신 10,000 / 10,000, 커밋 123 ms · 캡처 완료 1,608 ms, LSN 단조 증가 확인
    지연 볼 때 시계 편차도 같이 재야 함 측정 편차 5 · 7 · 9 ms (허용 500 ms = 목표 지연의 10%). 허용치를 넘으면 그 회차 커밋 기준 지연을 판정에서 뺀다 — 검증과 운영 경보에 같은 규칙
    이 처리량은 캡처만의 수치라 운영 처리량이 아님 반영 계측 리포트에 그 사실이 함께 기록된다. 운영 처리량은 rate(cdc_events_total[1m]) 로 따로 재고 두 값을 같이 읽는다
    필드 변경 식별 기능 추가 및 모니터링 강화 반영 변경 이력 표(cdc_change_audit)로 구현. 지표가 아니라 표인 이유는 변경 필드명을 레이블로 쓰면 카디널리티가 터지기 때문. 비용 때문에 테이블별로만 켠다(현재 car)
    REPLICA IDENTITY FULL 이 전제 측정 맞다 — car 를 DEFAULT 로 내리자 감사 기록이 identifiable = false("판정 못 함")가 됐고, FULL 로 되돌리자 changed_fields = price,updated_at 로 남았다 (V5-b 측정)

    V1 결론

    통과. 단건 지연은 여유가 크고, 필드 단위 변경 식별도 값까지 됩니다. 주의할 것은 지연을 결정하는 것이 건수가 아니라 트랜잭션 크기라는 점입니다 — 1만 건 버스트에서 예산에 가까워집니다.

    V2Provider Down case

    통과 기준 — 유실 0건 + 다운 허용시간(디스크 한계) 산출. 앞의 절반은 통과했고, 뒤의 절반은 지금도 미측정입니다.

    시나리오 문서의 항목상태근거
    꺼져 있던 구간의 변경분이 하나도 빠지지 않고 도착하는지 측정 다운 중 1,000건 → 재기동 후 1,000 / 1,000, 유실 0. 다운 시간 2,046 ms
    꺼져 있는 동안 WAL 이 얼마나 쌓이는지 측정 슬롯이 붙잡은 WAL 161.9 KiB, 변경 1건당 165 bytes
    DB 로그 쌓이는 양 모니터링 반영 cdc_slot_lag_bytes · cdc_slot_active · cdc_wal_size_bytes(pg_ls_waldir() 합계) · node-exporter 디스크 여유까지 수집 중
    다운 허용시간 산출 (= 디스크 여유 / WAL 증가율) 측정 산출됨. 디스크 여유 7.5 GiB(/var/lib, node-exporter 실측)와 165 bytes/변경으로 계산하면 변경 1,000/s 부하에서 13.5시간, 10,000/s 에서 1.4시간. 전체 표는 10절. 상한을 걸면 이 값이 그만큼 짧아진다
    max_slot_wal_keep_size 를 어떻게 할지가 V2 의 결론 판단 현재 -1(상한 없음). -1 이면 허용시간이 "디스크 찰 때까지"이고, 상한을 걸면 허용시간이 숫자로 나오는 대신 초과 순간 슬롯이 무효화되어 V3 상황으로 넘어간다. 디스크 고갈이냐 재동기화냐를 정하는 것이 이 항목
    165 bytes/변경 은 REPLICA IDENTITY FULL 기준인 점 주의 측정 교정 필요. 같은 부하를 두 설정에서 재보니 INSERT 는 DEFAULT 166 B / FULL 166 B (1.00배) 로 차이가 없다. V2 수치는 INSERT 1,000건으로 잰 값이라 REPLICA IDENTITY 와 무관하다 — FULL 의 대가는 UPDATE/DELETE 에서만 나타난다(V5-b)
    V5 요구가 V2 디스크 압력을 키우고 있는 구조 측정 맞다, 다만 조건부다. 대용량 컬럼이 없는 표는 UPDATE 1.12배 · DELETE 1.22배. 대용량 컬럼이 있으면 그 컬럼을 건드리지 않은 UPDATE 한 건이 656배가 된다(V5-b)
    다운 시간을 2초 / 1분 / 10분 으로 늘려가며 WAL 증가가 선형인지 미측정 현재 시나리오는 2초 구간 한 점만 잰다. 허용시간을 외삽하려면 최소 세 점이 필요하다
    재기동 후 실제 DB 데이터 건수·정합성 확인 측정 재기동 후 수신 1,000/1,000 · 유실 0 으로 확인. 값 정합은 V6 의 체크섬 대사가 별도로 판정한다

    V2 결론

    유실 0 은 확인됐고, 다운 허용시간도 이번에 숫자로 나왔습니다(10절). 남은 것은 재는 일이 아니라 고르는 일입니다 — max_slot_wal_keep_size 상한을 걸면 허용시간이 그만큼 짧아지는 대신 초과 순간 슬롯이 무효화되어 V3 로 넘어갑니다. 그 상한은 V4 의 "중복으로 복구 가능한 최대 폭"과 같은 값이라 두 항목을 같이 정해야 합니다.

    V3캡처 연결고리가 끊기는 경우 — 복구 불가능 구간 탐지

    통과 기준 — 유실 발생을 자동 탐지 + 재동기화 절차 문서화. 탐지·복원 모두 확인됐습니다.

    시나리오 문서의 항목상태근거
    슬롯을 강제 삭제한 뒤 재기동 — 시스템이 스스로 인지하는지 측정 끊긴 구간 100건 중 재기동 후 0건 수신, 엔진이 예외를 내고 종료, 슬롯을 새로 만들지 않음(false), 가드가 탐지함(true)
    탐지 근거 측정 SlotContinuityGuard 가 저장된 오프셋 LSN(0/2327B190)과 슬롯 restart_lsn(null)을 대조. fail-on-capture-gap: true 로 기동 거부
    재동기화(관심 테이블 재적재)로 정합을 복원하는 절차 측정 재동기화 전 50 / 101 → 후 101 / 101 복원
    탐지가 로그 예외뿐이라 prometheus 에 안 올라옴 → 경보 연결할 것 반영 cdc_capture_gap 게이지 + CdcCaptureGap 경보, 런타임 정지는 cdc_pipeline_halts_total + CdcPipelineHalted. 기동 시 정지는 게이지가, 런타임 정지는 카운터가 맡도록 나눠 놓았다
    슬롯이 삭제되는 것보다 무효화되는 게 실무에서 더 잦음 → wal_status 감시 반영 exporter 에 wal_status 를 정렬 가능한 cdc_slot_status_code 로 노출. 경보 CdcSlotWalUnreserved(>= 2, 곧 잘림) · CdcSlotWalLost(== 3, 즉시). safe_wal_size 도 함께 수집
    DB 이중화 후 같은 상황이 생기는지 확인 반영 "생기는지 확인"이 아니라 이미 정해진 결과다 — PostgreSQL 16 은 논리 복제 슬롯을 standby 로 동기화하지 않으므로 페일오버하면 슬롯이 사라진다. 승계해 주는 sync_replication_slots 는 17부터다. 지금 이미지가 16 이라 버전 선택이 곧 대응책이다
    확인 항목을 "페일오버 후 재동기화에 얼마나 걸리고 데이터가 얼마나 되는지"로 바꿀 것 미측정 슬롯 삭제로 같은 상태를 만들어 복원 자체는 확인했으나(101/101), 실제 데이터 규모에서의 소요 시간은 안 쟀다. 재동기화 시간은 대상 표 크기에 비례하므로 PoC 규모(101행)의 값은 외삽에 쓸 수 없다
    재적재만으로는 정합이 안 맞음 — 원본에서 사라진 행 처리 필요 측정 맞다. 재동기화는 멱등 UPSERT 라 중복 적재는 안전하지만 원본에서 사라진 행은 재적재로 지워지지 않는다. 절차에 "target 에만 남은 행 찾아서 처리" 단계가 필요하고, 소프트 삭제 표는 deleted 플래그로, 하드 삭제 표는 별도 대사로 다뤄야 한다

    V3 결론

    조용히 넘어가지 않는다는 것이 확인됐고, 탐지 결과가 지표·경보로도 나갑니다. 남은 것은 페일오버 실측과, 그 앞단의 PostgreSQL 버전 선택입니다.

    V4같은 이벤트가 두 번 오는 경우 — 이중 반영 제한

    통과 기준 — 중복 유입 시에도 최종 데이터 정합 유지. 기존 경로는 통과했고, 두 번째 경로에서 한 표가 실제로 되돌아갔습니다.

    시나리오 문서의 항목상태근거
    재기동 직후 마지막 처리분 이후 이벤트가 중복으로 다시 옴 (정상 동작) 측정 중복 200건 유입(같은 LSN), 1차 반영 200 / 2차 반영 0, 두 번 반영된 행 0. 원본 200 = 수신 200
    테이블마다 방어 기제가 달라서 하나만 보고 통과시키면 안 됨 → 테이블별로 돌릴 것 측정 운영 4개 표 전부에 대해 수행. computer · grade · member 는 LSN 가드가 0행 반영으로 차단. car 는 차단하지 못하고 최신 값이 격리 시점 값으로 되돌아갔다
    DLQ 재처리도 중복 유입 경로인데 V4 가 안 보고 있음 측정 격리 → 원인 수정 → 그 사이 정상 경로 갱신 → RETRY_REQUESTED 재처리 전 구간을 재현. 이 경로에서는 중복이 아니라 역전이 문제가 된다

    V4 에서 나온 것 — 조용한 역전

    car 의 회귀는 파이프라인 어디에도 오류를 남기지 않습니다. 적재는 성공(1행 갱신)했고 DLQ 는 RESOLVED 가 되고 지표도 정상입니다. 알려주는 신호는 대사(V6)의 체크섬 불일치 하나뿐이고, 그것도 대사 주기가 돌아온 뒤입니다.

    부수 발견 — DLQ 는 재처리 결과를 예외 유무로만 판정합니다. 가드에 막혀 0행이 반영돼도 RESOLVED 가 되므로, 상태만으로는 "반영됨"과 "차단됨"을 구분할 수 없습니다. 네 표가 모두 RESOLVED 였지만 실제로 값이 바뀐 것은 car 하나뿐이었습니다.

    V5이벤트가 비어서 오는 경우 (TOAST)

    통과 기준 — 관심 필드가 모든 이벤트에서 항상 판독 가능. 해소 방법은 확인됐고, 이번에 판별 절차와 대가가 채워졌습니다.

    시나리오 문서의 항목상태근거
    UPDATE 시 변경되지 않은 대용량 필드가 이벤트에 안 실리는 상황 재현 측정 DEFAULT 에서 after.big_payload 가 자리표시자(__debezium_unavailable_value), before 없음 → 현재 값 판독 불가. INSERT 에는 200,000 bytes 온전히 실린다
    REPLICA IDENTITY 변경으로 해소되는지 측정 FULL 로 바꾼 뒤 before / after 양쪽 200,000 bytes 온전히 실려 복원 가능
    관심 필드가 걸리는지 판별하는 방법을 정해둬야 실행이 됨 측정 2단계 절차로 확정. 1단계 정적 선별 scripts/toast-candidates.sql(reltoastrelid <> 0 → attstorage <> 'p' → max(pg_column_size) >= 2032), 2단계 동적 확정(관심 필드를 건드리지 않는 UPDATE 를 흘려 자리표시자 확인). 규칙이 동작을 예측하는지까지 검증 — 후보만 판독 불가, 비후보는 정상
    지금 스키마가 이 케이스에 걸리는가 측정 걸리지 않는다. 캡처 대상 5개 표의 toastable 컬럼 13개 중 후보 0개, 가장 큰 컬럼이 member.email 17 bytes (임계 2,032 bytes)
    FULL 로 바꿨을 때 대가가 얼마인지 측정 아래 표. 대용량 컬럼 유무로 두 세계로 갈린다
    대용량 필드 없는 테이블까지 FULL 로 둘지 테이블별로 판단 측정 computer 는 DEFAULT 로 내려도 INSERT · UPDATE · 소프트 삭제가 모두 정상(핸들러가 before 에서 PK 만 읽음). car 는 V1 감사 로그 때문에 못 내린다 — DEFAULT 에서 identifiable = false

    REPLICA IDENTITY FULL 의 대가

    표 / 연산DEFAULTFULL증가율읽는 법
    좁은 표 · INSERT166 B166 B1.00 배새 행에는 "변경 전 행"이 없다
    좁은 표 · UPDATE342 B381 B1.12 배변경 전 행 하나가 더 붙는다
    좁은 표 · DELETE146 B177 B1.22 배DEFAULT 는 PK 만, FULL 은 행 전체
    넓은 표 · INSERT214,310 B214,310 B1.00 배값 자체가 크니 설정과 무관
    넓은 표 · UPDATE306 B200,925 B656 배건드리지도 않은 200 KB 를 꺼내 WAL 에 넣는다
    넓은 표 · DELETE211,266 B411,890 B1.95 배DEFAULT 도 이미 비싸다(TOAST 페이지 FPI 2,509개)

    V5 결론 — 증상과 비용은 같은 동전의 양면

    DEFAULT 에서 그 컬럼을 건드리지 않은 UPDATE 는 TOAST 포인터를 재사용하므로 값이 WAL 에 실리지 않습니다. 그래서 이벤트에서도 빠지는 것이고(=V5 의 증상), 대신 306 bytes 로 끝납니다. 읽히게 하려면 실어야 하고, 그 순간 656배가 됩니다.

    현 스키마에는 후보 컬럼이 없어 좁은 표 기준 12~22% 만 더 쓰고 있습니다. 그래서 전 테이블 FULL 유지가 정당화되지만, 대용량 컬럼이 하나 추가되는 순간 그 표의 비용이 세 자릿수 배로 바뀝니다.

    V6최종 안정성 검증 — 대사와 heartbeat

    통과 기준 — 인위적 유실 주입 시 대사에서 검출됨. 검출은 확인됐고, 이번에 대사가 통과하는데 깨져 있는 경우가 드러났습니다.

    시나리오 문서의 항목상태근거
    정상 상태에서 건수/체크섬 대조 측정 300 / 300 체크섬 일치(0a826cc7…)
    인위적 유실 주입 시 검출 측정 3건 삭제 → 건수차 3, 대사 불일치
    갯수는 같지만 내용이 다를 수 있음 → 확인 필요 측정 맞는 판단. 행을 지우지 않고 금액만 올렸을 때도 불일치로 검출 — 건수 대사만으로는 부족하다
    heartbeat 이 통과 기준에 있는데 설정 자체가 안 들어가 있음 반영 heartbeat-interval-ms: 10000 + heartbeat-action-query(publication 에 든 표에 쓰기) 를 application.yml 에 반영. 전용 표 cdc_heartbeat 를 publication 과 table-include-list 양쪽에 넣었다
    interval 만 켜면 슬롯이 안 움직임 / action.query 를 같이 걸어야 함 측정 간격만: 슬롯 전진 0 bytes(confirmed_flush_lsn 그대로, 붙잡은 WAL 104 → 43,568 bytes). 간격+action.query: 33,848 bytes 전진
    DLQ 건수도 대사에 넣어야 함 — 판정식 source − target − DLQ(PENDING) = 0 반영 exporter cdc_dlq_total_pending · cdc_dlq_rows, 경보 CdcReconcileMismatch 가 그 판정식을 그대로 쓴다. 대시보드 패널도 추가됨
    그 판정식이 무엇을 놓치는가 측정 격리된 행이 부모였을 때. 부모 1건 격리 상태에서 판정식은 0(통과) 인데 고아 참조가 1건 있었다. 재처리 후 둘 다 0
    관계 있는 테이블은 고아 참조 대사가 따로 필요 반영 측정 exporter cdc_orphan + 경보 CdcOrphanRows. 관계를 목록으로 적지 않고 <부모>_id 이름 규칙으로 카탈로그에서 찾는다. 위 시나리오로 실제 검출까지 확인
    야간 배치나 최근 N시간 구간 한정으로 돌리는 전략 수립 및 적용 측정 scripts/reconcile.sql 이 표별로 전체·구간 대사를 한 번에 낸다. 5만 행에서 전체 146 ms → 구간(2%) 12 ms. 대가는 아래

    표건수 대사체크섬 대사구간 대사

    구간 한정의 대가 — 실측

    구간 밖(2일 전) 행 1건의 값만 바꾸고 updated_at 은 건드리지 않았더니 전체 대사는 검출, 구간 대사는 검출하지 못했습니다. 수신 측에서 값이 조용히 어긋나는 상황이 정확히 이 모양이라, 두 대사는 대체재가 아니라 짝입니다 — 상시로 구간을 돌려 빨리 잡고, 야간 배치로 전체를 훑습니다. 최대 탐지 지연 = 야간 배치 주기가 됩니다.

    예상과 달랐던 것: 비용을 만드는 것은 스캔이 아니라 정렬·집계였습니다. 인덱스 없이도 구간을 2%로 좁히는 것만으로 146 ms → 12 ms 가 됐고, 인덱스는 읽는 방식만 바꿨을 뿐(11 ms) 시간은 같았습니다.

    07완료 조건 — 운영 전환시 권고 설정값

    시나리오 문서가 제시한 권고 설정값에 현재 상태와 근거를 붙였습니다.

    설정문서의 권고현재근거 / 남은 것
    max_slot_wal_keep_size -1 → 디스크 여유의 20~30% 미적용 상한을 걸면 허용시간이 숫자로 나오지만 초과 순간 슬롯이 무효화되어 V3 로 넘어간다. 그 값이 곧 V4 의 "중복으로 복구 가능한 최대 폭" — 두 항목을 같이 정해야 한다
    heartbeat.interval.ms 미설정 → 10000 적용 단독으로는 슬롯 전진 0 bytes (V6 측정) — 아래 항목과 반드시 함께
    heartbeat.action.query 미설정 → publication 표에 쓰기 적용 병행 시 슬롯 전진 33,848 bytes (V6 측정). 전용 표 cdc_heartbeat 와 권한(cdc_user)까지 함께 들어가야 동작한다
    REPLICA IDENTITY 전 테이블 FULL 유지하되 테이블별로 재검토 적용 재검토 결과: 유지 권고. 후보 컬럼 0개이고 좁은 표 비용이 12~22% 로 작다. 단 car 는 V1 감사 때문에 내릴 수 없고, 대용량 컬럼이 생기면 656배가 되므로 스키마 변경 절차에 선별 질의를 넣어야 한다
    오프셋 저장 FileOffsetBackingStore + 볼륨 유지 + 수신측 체크포인트 병행 적용 cdc_checkpoint 표가 있어야 볼륨이 날아갔을 때 "처음부터"와 "건너뜀"을 구분할 수 있다 (V3 가드의 판정 근거)
    offset.flush.interval.ms 10000 유지 적용 줄이면 중복 폭은 줄지만 I/O 가 는다. 중복은 V4 가드가 이미 막으므로 유지가 맞다
    슬롯 lag 경보 없음 → warn 512MB / crit 2GB 적용 CdcSlotLagWarning / CdcSlotLagCritical. 165 bytes/변경 기준으로 환산한 값
    wal_status 미감시 → unreserved 경고, lost 즉시 적용 cdc_slot_status_code + CdcSlotWalUnreserved(>=2) / CdcSlotWalLost(==3)
    fail-on-capture-gap true 유지 + 메트릭 노출 적용 cdc_capture_gap 게이지 + CdcCaptureGap 경보. 예외를 던져 컨텍스트를 죽이는 대신 엔진만 안 띄우고 앱은 살려 지표를 내보낸다 — 탐지해 놓고 신호를 못 내면 탐지한 적 없는 것과 같다

    08완료 조건 — Debezium 자체 결함 판단 기준

    문서는 "재현 시 판단"이라고만 되어 있고 판단 기준이 없었습니다. 그러면 장애 한 번에 전환 논의가 됩니다. 기준을 아래로 고정합니다.

    항목판정 기준
    재현 요건같은 시나리오 3회 이상 재현 + 최신 패치 버전에서도 재현 + 업스트림 이슈 존재 여부 확인
    행업(hang)엔진 스레드는 살아 있는데 이벤트 0건이고 슬롯이 10분 이상 안 움직임. 지표로는 CdcSlotNotAdvancing 과 cdc_events_total 정체가 동시에
    오프셋 오염재기동 시 저장 LSN 이 슬롯 restart_lsn 보다 뒤로 감. SlotContinuityGuard 가 이미 잡으므로 그 로그가 근거가 된다
    메모리 누수24시간 부하에서 GC 이후에도 heap 이 단조 증가

    대안 두 개는 등가가 아니다

    버전 컬럼 폴링은 DELETE 를 못 잡습니다. 지워진 행은 조회에 안 나오므로, 이 대안을 쓰려면 원본이 소프트 삭제를 쓴다는 전제가 필요합니다.
    논리 복제 직접 소비(pgjdbc replication API)는 가능은 하지만 슬롯·오프셋·스키마 변경 처리를 직접 만들어야 합니다 — V2~V4 에서 검증한 것을 다시 만드는 셈입니다.

    그래서 전환 판단의 첫 질문은 "debezium 이 불안정한가"가 아니라 "원본 테이블에 소프트 삭제를 강제할 수 있는가"입니다. 안 되면 선택지가 사실상 하나입니다.

    09「아직 안 한 것」 현황

    시나리오 문서 말미의 5건 — 결론은 났는데 코드나 설정에 안 들어간 것들입니다. 전부 반영됐습니다.

    항목상태어디에 들어갔는가
    heartbeat.interval.ms + heartbeat.action.query 설정 추가 (V6) 완료 application.yml cdc.source.heartbeat-*, 전용 표 cdc_heartbeat 와 cdc_user 권한
    exporter 쿼리에 wal_status / safe_wal_size 추가하고 경보 연결 (V3) 완료 queries-source.yaml cdc_slot_status_code · safe_wal_size_bytes, 경보 2건
    cdc_dead_letters_total 대시보드 패널 추가 (V6) 완료 queries-target.yaml cdc_dlq_total · cdc_dlq, PoC · 검증 대시보드 양쪽에 패널
    capture-gap 탐지 결과 메트릭으로 노출 (V3) 완료 cdc_capture_gap 게이지 + CdcCaptureGap · CdcCaptureGapByLsn 경보
    pg_ls_waldir() 합계 수집 + node_exporter 도입 (V2) 완료 cdc_wal_size_bytes · cdc_wal_files, node-exporter 컨테이너 + CdcWalDiskHeadroomLow 경보

    그래서 지금 남은 것은 코드가 아니다

    「아직 안 한 것」 5건은 전부 들어갔고 회귀 시나리오가 지키고 있습니다. 남은 것은 수치를 정하는 일(상한값·주기)과 스키마·절차 판단입니다 — 다음 절.

    상한을 걸면 이 값이 짧아진다

    위 표는 max_slot_wal_keep_size = -1(상한 없음) 기준이라 "디스크가 찰 때까지"입니다. 권고안대로 디스크 여유의 20~30% 를 상한으로 걸면 — 1.5 GiB(20%) 에서 변경 1,000/s 기준 2.7시간, 2.2 GiB(30%) 에서 4.1시간 입니다. 그 시간을 넘기면 디스크는 안전한 대신 슬롯이 무효화되어 V3(재동기화) 로 넘어갑니다.

    고를 것은 시간이 아니라 실패 방식입니다 — 디스크 고갈로 DB 전체가 멈추느냐, 슬롯을 버리고 재동기화하느냐. 이 표는 그 선택지에 시간을 붙여 줄 뿐입니다.

    이 절을 쓰면서 발견한 것 두 가지

    1. 지표 이름만 보고 "있다"고 하면 안 됩니다. 처음 조회할 때 node_filesystem_avail_bytes{mountpoint="/"} 로 물어 빈 결과를 받았습니다. 이 컨테이너에는 / 마운트가 노출되지 않고 /var/lib 가 실제 대상이었습니다. 경보식은 그것을 알고 mountpoint="/var/lib" 를 쓰고 있어 정상 동작하지만, 라벨이 맞는지까지 봐야 "경보가 뜬다"고 말할 수 있습니다.

    2. cdc_pipeline_halts_total 은 시계열이 아예 없습니다. 정지가 한 번도 없었기 때문이고, 경보식이 increase(...[10m]) > 0 이라 동작에는 문제가 없습니다(시계열이 생기는 순간 발화). 다만 대시보드 패널은 0 이 아니라 "No data" 로 보이므로, 패널만 보고 "정지 감시가 없다"고 오해할 여지가 있습니다.

    여전히 경보로 연결되지 않은 것

    건수 대사와 고아 참조는 exporter 가 상시로 내고 경보도 걸려 있지만, 체크섬 대사는 경보 22건 어디에도 없습니다 — 스크립트로만 돌아가기 때문입니다. 값이 조용히 어긋난 경우(V4 의 car 회귀, V6 의 구간 밖 변조)를 잡는 것이 바로 체크섬 대사인데, 그것이 사람이 돌려야만 도는 상태입니다. 11절의 "대사 실행 주체 결정" 이 가리키는 빈자리입니다.

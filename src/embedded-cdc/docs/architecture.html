왜 이 구조인가

두 가지 큰 선택이 이 파이프라인의 성격을 결정한다.

선택 1 — 로그 기반 CDC (폴링·트리거가 아니라)

변경을 잡는 방법은 여러 가지다(주기적 SELECT 폴링, 테이블 트리거, 타임스탬프 비교…). 이 프로젝트는 PostgreSQL이 이미 쓰고 있는 트랜잭션 로그(WAL)를 구독하는 방식을 쓴다. 원천 테이블에 부하를 주지 않고, 놓치는 변경이 없으며, DELETE까지 잡을 수 있는 유일한 방식이기 때문이다. 이를 위해 source DB에는 세 가지 설정이 필요하다:

설정값역할
wal_levellogicalWAL에 논리 디코딩용 정보를 추가로 기록. 이것이 없으면 로그 기반 CDC 자체가 불가능
max_wal_senders10WAL을 외부로 스트리밍하는 프로세스 수
max_replication_slots10replication slot 수. Debezium이 slot 하나(embedded_cdc_slot)를 점유

디코딩 플러그인은 pgoutput — PostgreSQL 10+에 내장되어 있어 별도 확장 설치가 필요 없다. 캡처 대상은 publication(embedded_cdc_pub)으로 지정하고, 계정은 REPLICATION 속성과 snapshot용 SELECT만 가진 최소 권한 전용 계정(cdc_user)을 쓴다.

선택 2 — Kafka 없이 Embedded Engine

Debezium의 표준 배포는 Kafka Connect 위에서 돌지만, 이 프로젝트는 Debezium을 라이브러리로 Spring 앱 안에 내장했다. 움직이는 부품이 DB 둘 + 서비스 하나로 줄어 이해하기 쉽고, 컨테이너 4개 compose로 전부 띄울 수 있다.

Kafka Connect 배포Embedded Engine (이 프로젝트)
중간 브로커Kafka 클러스터 + Connect 클러스터 필요없음 — 앱이 직접 수신
offset 저장Kafka topic (고가용)로컬 파일 offsets.dat (named volume)
이벤트 순서파티션 단위 보장단일 스레드 — WAL 순서 그대로
적합한 곳다수 컨슈머 · 운영 규모단일 컨슈머 · 학습 · PoC · 소규모 동기화
Trade-off

offset을 로컬 파일이 떠안으므로 파일이 사라지면 snapshot이 재실행된다. 모든 sink 쓰기가 멱등(UPSERT)이라 재실행돼도 target은 깨지지 않는다 — 이것이 멱등성이 필수인 이유다.

이벤트의 일생

source에서 UPDATE 한 건이 일어나면 무슨 일이 벌어지는가.

1 · COMMIT
source에서 트랜잭션 커밋 → WAL에 기록
2 · pgoutput 디코딩
WAL 바이너리를 논리 변경(행 단위)으로 해석
3 · Debezium 이벤트
before/after/op/lsn을 담은 JSON 생성
▼
4 · Parser
JSON → RowChange(table, op, before, after, lsn)
5 · Dispatcher
테이블 이름으로 CarSink / ComputerSink 선택
6 · Sink
target에 멱등 UPSERT 또는 (소프트) 삭제
▼
7 · 지표 기록
처리량 +1, 지연(now − ts_ms) 기록
8 · offset 커밋
"여기까지 읽음"을 offsets.dat에 주기 저장(10s)

Debezium이 만드는 이벤트의 실물은 이렇게 생겼다 (computer UPDATE의 예, 요약):

{
  "before": { "id": 2, "brand": "Lenovo", "model": "ThinkPad X1", "ram_gb": 32, ... },
  "after":  { "id": 2, "brand": "Lenovo", "model": "ThinkPad X1", "ram_gb": 48, ... },
  "source": { "table": "computer", "lsn": 26710648, "ts_ms": 1787732895241, ... },
  "op": "u"
}

rsnapshot(최초 전체 복사) · cINSERT · uUPDATE · dDELETE. before에 전체 컬럼이 담기는 것은 source 테이블에 REPLICA IDENTITY FULL을 걸었기 때문이다 — 기본값이면 PK만 담겨서, DELETE를 소프트 삭제로 기록할 때 정보가 부족하다.

스키마 매핑 — 같은 경우와 다른 경우

테이블 두 개가 CDC의 두 대표 시나리오를 하나씩 맡는다. 관계(FK)는 아직 없다.

car — 스키마가 같은 경우 (1:1 복제)

source와 target의 컬럼이 완전히 같다. sink는 변환 없이 그대로 UPSERT하고, DELETE는 물리 삭제한다. 유일한 차이는 target의 id가 BIGSERIAL이 아니라 BIGINT라는 것 — 발번은 source만 한다.

computer — 스키마가 다른 경우 (변환 + 정확성 장치)

source 컬럼변환target 컬럼
brand, model이어붙임full_name — "Lenovo ThinkPad X1"
cpu, ram_gb이어붙임spec — "Core Ultra 7 / 48GB"
price_usd× 1350 (데모용 고정 환율)price_krw

여기에 원본에는 없는 부가 컬럼 3개가 target에만 붙는다. 각각 실제 장애 시나리오 하나씩을 막는다:

컬럼막는 문제
deleted (소프트 삭제)물리 삭제하면, 순서가 꼬여 늦게 도착한 UPDATE가 UPSERT로 죽은 행을 되살린다. 삭제는 플래그만 세운다
source_lsn (순서 가드)UPSERT의 WHERE EXCLUDED.source_lsn > computer.source_lsn 조건이 더 오래된 이벤트의 덮어쓰기를 차단. LSN은 WAL 위치라 단조 증가하는 정수 — 가장 확실한 순서 판정 키
synced_at"이 행이 언제 마지막으로 동기화됐나"를 행 단위로 남겨 지연·장애 조사를 돕는다
비가역적 선택

이 설계는 target 행을 항상 최신값으로 덮어쓴다(SCD 유형 1). 이력은 남지 않고, 나중에 복원할 수도 없다. 변경 이력이 필요하다면 처음부터 버전 행을 쌓는 유형 2로 시작해야 한다.

운영 시 주의

Replication slot — 가장 무거운 실패 모드

slot은 만료되지 않는다. cdc-service가 오래 죽어 있으면 slot이 붙잡은 WAL이 source DB에 무한정 쌓여 디스크를 고갈시킨다 — 파이프라인 장애가 원천 DB 장애로 번지는 것이다. 대시보드의 cdc_slot_lag_bytes가 계속 자라면 서비스를 살리거나, 파이프라인을 접을 거면 slot을 삭제해야 한다: SELECT pg_drop_replication_slot('embedded_cdc_slot');

전달 보장

이 파이프라인은 at-least-once다. 같은 이벤트가 두 번 올 수 있는 것이 정상 동작이고, 모든 쓰기가 멱등이라 결과는 같다. 단, sink 오류를 삼키고 계속 가는 정책이므로 cdc_sink_errors_total이 0이 아니면 그 이벤트는 유실된 것 — 대시보드가 빨간불을 켠다.

스키마 변경(DDL)

컬럼 추가 등 DDL은 자동으로 target에 전파되지 않는다. source에 컬럼을 더하면 target 스키마와 sink의 매핑 코드를 함께 고쳐야 한다.

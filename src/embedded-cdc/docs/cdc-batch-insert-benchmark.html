CDC 대량 INSERT 반영 시간 측정

2026-09-02 11:15~13:21 KST · feature/go-cdc

    Measurement Report

    배치 크기별 CDC 반영 시간 측정 결과

    테이블당 1,000행부터 1,000,000행까지 열두 번의 배치 INSERT를 넣고, Debezium Embedded(Java) 스택과 go-pq-cdc(Go) 스택이 각각 target DB에 반영을 끝내기까지 걸린 시간을 Prometheus 원본 시계열에서 산출했습니다.

    측정 2026-09-02 11:15~13:21 배치 12종 · 스택 2종 해상도 5초 (scrape 간격) 테이블당 1,000 ~ 1,000,000행

    00측정 범위와 전제

    같은 시드를 두 스택에 각각 넣고 반영 완료 시각만 비교했습니다. 무엇을 재지 않았는지가 결과 해석을 좌우합니다.

    측정한 것

    • source DB의 INSERT 소요 시간 (WAL 생성 구간)
    • source 커밋부터 target 3개 테이블 반영 완료까지의 시간
    • 구간 평균 처리량 (행/초)
    • cdc-service 컨테이너의 CPU · 메모리 최대치

    측정하지 않은 것

    • UPDATE · DELETE 반영 시간 (이번 배치는 INSERT만)
    • 두 스택 동시 부하 시의 상호 간섭 (source DB가 서로 분리되어 있음)
    • 두 스택의 end-to-end 지연 지표 절대 비교 — 기준 시각이 다릅니다 (07절)
    • 재기동 후 스냅샷 재적재 시간

    전제

    두 스택은 컨테이너 · 포트 · 네트워크 · 복제 슬롯이 모두 분리되어 있고 source DB도 각각 따로 띄웁니다. 같은 시드 SQL을 두 source DB에 각각 실행했으므로 source INSERT 소요는 스택별로 다른 값입니다. 같은 호스트(Windows 11 + podman)에서 동시에 돌았으므로 CPU · 디스크는 공유합니다.7

    01측정 방법과 지표 정의

    대시보드 그래프를 눈으로 읽는 대신 Prometheus 원본 시계열에서 계단이 오른 시각을 직접 뽑았습니다.

    t1 커밋 완료source 행 수가 계단식으로 오른 시점 (테이블 3개 중 최초) cdc_source_rows{table_name=...}3

    박스를 끌어 배치를 바꿀 수 있습니다. 구조를 고쳤으면 JSON 버튼으로 내보내 이 파일의 dgm-data 블록에 붙여넣습니다.

    읽는 법

    1,000행과 10,000행 배치는 반영이 scrape 간격(5초) 안에 끝나 처리량이 의미 없는 값으로 나옵니다. 100,000행부터가 유효한 측정 구간입니다. 900,000행까지는 반영 시간이 배치 크기에 거의 정비례하고, 1,000,000행에서 처음 그 선을 넘습니다. 가장 큰 1,000,000행 배치는 13:10:38에 커밋이 시작돼 13:20:48(Java) · 13:20:28(Go)에 반영이 끝났습니다.

    Go의 900,000행 배치는 측정값으로 쓸 수 없습니다

    Go cdc-service가 12:54:17부터 13:04:47까지 10분 30초 동안 내려가 있었고, 900,000행 커밋(12:55:03)이 그 사이에 일어났습니다. 기록된 925초는 반영 속도가 아니라 정지 시간 + 재기동 후 복구 시간입니다. 재기동(13:04:38) 이후 밀려 있던 2,700,000행을 350초에 흡수했으므로 복구 자체는 정상이었지만, 같은 조건의 비교값이 아니므로 표에서 제외했습니다. 이 사건 자체는 05절에 따로 적었습니다.

    03테이블별 분해 — 반영은 커밋 순서대로 직렬화됩니다

    한 배치가 3개 테이블에 들어가지만 CDC 스트림은 하나입니다. 뒤에 커밋된 테이블은 앞 테이블이 다 빠질 때까지 기다립니다.

    테이블source 커밋 Java 반영 완료Java 소요 Go 반영 완료Go 소요
    car11:37:2511:39:20115초11:39:30120초
    computer11:37:3011:41:25235초11:41:35240초
    member11:37:5011:43:45355초11:43:35345초

    700,000행 배치 기준입니다. 세 테이블의 커밋 시각 차이는 25초 이내인데 반영 완료는 115초 → 235초 → 355초로 벌어집니다. 차이는 처리 난이도가 아니라 대기 순번입니다. car가 다 빠진 뒤 computer가, 그다음 member가 처리됩니다. 마지막 테이블의 지연은 앞선 두 테이블의 처리 시간을 그대로 물려받습니다.

    배치를 키워도 모양은 같습니다. 800,000행에서 Java 140초 · 285초 · 430초, Go 140초 · 290초 · 410초. 1,000,000행에서는 Java 170초 · 385초 · 580초, Go 175초 · 390초 · 555초로 car → computer → member 순서대로 빠집니다.

    두 스택의 처리량은 사실상 동률입니다

    100,000행 이상 구간에서 Java 4,918~6,000행/초, Go 5,128~6,316행/초입니다. 차이는 3~7% 수준이고 배치마다 순위가 뒤집히므로, 이 측정으로 "어느 쪽이 빠르다"고 말할 수 없습니다. 두 스택 모두 target DB의 UPSERT 처리 속도에 묶여 있다고 보는 편이 관측에 맞습니다.

    Go 쪽 메모리가 배치 크기를 따라 계속 오릅니다

    Java는 900MB 부근에서 평평합니다(JVM 힙 상한에 눌린 모습). Go는 43MB에서 시작해 1,000,000행 배치에서 2,138MB까지 올랐고, 200,000행과 300,000행 사이에서 44MB → 634MB로 한 번 크게 튑니다. 배치가 커질수록 미반영 변경분을 프로세스 안에 더 오래 들고 있다는 뜻입니다. 배치 크기와 거의 비례해 오르므로, 컨테이너에 메모리 상한이 걸려 있지 않은 지금 구성으로 더 큰 배치를 넣으면 호스트 메모리를 먼저 소진합니다. 다음 측정 전에 mem_limit 을 걸고 한계 지점을 확인해야 합니다.

    05관찰 정리

    숫자에서 바로 읽히는 것만 적었습니다. 추정이 섞인 항목은 그렇게 표시했습니다.

    관찰근거의미
    병목은 source가 아니라 반영 쪽 100만행 배치: source INSERT 35~40초 vs 반영 585~610초 소스 쓰기가 끝난 뒤에도 6분간 target이 뒤따라옵니다. 정합성 확인은 그 시간을 기다린 뒤 해야 합니다.
    반영 시간은 배치 크기에 선형 10만 50초 → 20만 100초 → 40만 210초 → 70만 380초 → 90만 475초 (Java 기준) 90만행까지는 유지됩니다. 100만행에서 Java 610초로 예상치(약 530초)를 넘겨 처음 이탈했습니다.
    처리량은 4,900~6,300행/초 두 스택 · 모든 배치 구간 구현 언어보다 target UPSERT 비용이 상한을 정하고 있습니다. 추정
    Java CPU가 항상 조금 더 높음 Java 약 1.0 core, Go 0.78~0.85 core 같은 처리량을 20% 더 많은 CPU로 냅니다.
    Go 메모리 우상향 43MB → 2,138MB (10만 → 100만) 장시간 대량 적재 시 컨테이너 메모리 상한 설정이 필요합니다.
    walsender 끊김은 설정으로 해소됨 wal_sender_timeout 1min → 5min6 이번 측정 구간에서는 재접속·panic이 재현되지 않았습니다.
    서비스가 내려가 있어도 변경은 남아 있다가 복구된다 Go cdc-service 정지 12:54:17~13:04:47, 그 사이 커밋된 2,700,000행을 재기동 후 350초에 흡수10 복구 처리량은 7,700행/초로 평상시(약 5,800행/초)보다 오히려 높습니다. 밀린 분량을 큰 묶음으로 처리하기 때문입니다. 추정
    단, 슬롯이 이미 버린 구간은 되받지 못한다 재기동 직후 로그: 슬롯 0/B358B288 vs 처리 완료 0/B33A5CC0 구간 유실 경고10 이번에는 행 수가 결국 일치했지만, 정지가 길어지면 재적재가 필요합니다. 정지 시간 감시가 필요한 근거입니다.

    06재현 절차

    같은 숫자를 다시 뽑는 순서입니다. 배치 크기만 바꿔 반복하면 표가 그대로 채워집니다.

    1. 스택 기동 (스택 루트에서)
    # Java 판
cd src/embedded-cdc      && docker compose up -d --build
# Go 판 (포트·네트워크가 달라 동시에 띄울 수 있다)
cd src/embedded-cdc-go   && docker compose up -d --build
    2. 배치 시드 투입 — 두 source DB에 같은 값으로
    # 테이블당 N행. member / car / computer 세 테이블에 각각 들어간다
podman exec -i emb-cdc-source-pg psql -U postgres -d sourcedb \
    -v ON_ERROR_STOP=1 -v cnt=1000000 -f - < src/embedded-cdc/scripts/seed-bulk.sql

podman exec -i emb-cdc-go-source-pg psql -U postgres -d sourcedb \
    -v ON_ERROR_STOP=1 -v cnt=1000000 -f - < src/embedded-cdc-go/scripts/seed-bulk.sql
    3. 계단이 오른 시각 추출 (Prometheus API)
    # source 행 수 — 값이 뛴 지점이 t1
curl -s "http://localhost:56090/api/v1/query_range?query=cdc_source_rows%7Btable_name=%22car%22%7D\
&start=$(date -d '-1 hour' +%s)&end=$(date +%s)&step=5"

# target 행 수 — source 값에 도달한 지점이 t2
curl -s "http://localhost:56090/api/v1/query_range?query=cdc_target_rows%7Btable_name=%22car%22%7D\
&start=$(date -d '-1 hour' +%s)&end=$(date +%s)&step=5"

# Go 판은 포트만 57090 으로 바꾼다
    4. 대시보드에서 눈으로 확인

http://localhost:56300/d/embedded-cdc/embedded-cdc-overview?orgId=1&refresh=5s
# Go

    재측정 시 확인할 것 0 / 0

    • 직전 배치의 반영이 완전히 끝난 뒤 다음 배치를 넣는다target 행 수 = source 행 수 확인. 겹치면 두 배치의 소요 시간이 섞인다
    • 두 source DB에 같은 cnt 값을 넣는다한쪽만 크면 비교가 성립하지 않는다
    • 호스트에서 다른 무거운 작업을 돌리지 않는다두 스택이 같은 CPU · 디스크를 공유한다
    • Prometheus 보존 기간 안에서 조회한다스택을 내렸다 올리면 이전 구간 시계열이 사라진다
    • Go 컨테이너 메모리 상한을 확인한다100만행 이상에서는 1.5GB를 넘을 수 있다
    • 시드 데이터에 실제 개인정보를 넣지 않는다seed-bulk.sql은 난수 조합 문자열만 생성한다

    07이 측정의 한계

    숫자를 인용하기 전에 읽어야 하는 부분입니다.

    한계영향대응
    해상도 5초모든 구간 값에 ±5초 오차. 10초짜리 값은 오차가 50%100,000행 이상 구간만 인용
    두 스택의 지연 지표 기준이 다름 Java는 커밋 시각 기준8, Go는 WAL 메시지 송신 시각 기준9. 70만행 배치에서 Java 최대 지연 355초, Go 127초로 찍혔지만 실제 반영 완료 시각은 10초 차이입니다 대시보드의 지연 패널로 두 스택을 비교하지 않는다. 행 수 기반 시각만 쓴다
    단일 호스트 · 컨테이너 환경두 스택과 DB 4개가 CPU · 디스크를 공유절대 성능치가 아니라 상대 비교용으로만 사용
    INSERT만 측정UPDATE는 인덱스 갱신, DELETE는 소프트 삭제 경로가 달라 다른 값이 나옴연산별 측정은 별도 수행
    Go의 900,000행 배치는 무효서비스가 12:54:17~13:04:47 내려가 있어 반영 시간이 아니라 정지+복구 시간이 기록됨10표에서 제외. Go 곡선은 800,000행과 1,000,000행으로 이음
    선형성 확인 범위는 100만행까지그 이상에서 큐가 급격히 밀리는지는 미확인. Go 메모리가 2.1GB에 도달다음 측정은 컨테이너 메모리 상한을 걸고 수행
    1회 측정같은 배치를 반복하지 않아 편차를 알 수 없음결론을 낼 배치는 3회 반복 후 중앙값 사용

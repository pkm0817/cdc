INSERT 한 건의 여정

embedded-cdc · 2026-08-27 · 작업트리 기준

    Development Document

    INSERT 한 건이 source 에서 target 까지 가는 길

    Kafka 없이 Debezium Embedded Engine 하나로 PostgreSQL 두 대를 잇는 파이프라인입니다. 이 문서는 SQL 한 줄이 커밋된 순간부터 target 테이블에 값이 앉을 때까지 어떤 단계를 지나고, 각 단계에서 무엇이 잘못될 수 있으며, 그것을 어떤 쿼리로 확인하는지를 정의합니다.

    실행 검증 완료 2026-08-27 Debezium 3.6.1.Final Kafka 없음 replication slot 상시 점유

    00이 문서가 답하는 것

    코드는 이미 돌고 있습니다. 그러므로 "무엇을 만들까"가 아니라 "지금 무엇이 일어나고 있고, 어디를 의심해야 하나"를 적습니다.

    다루는 것

    • 커밋된 행 하나가 WAL 을 거쳐 target 에 앉기까지의 7단계
    • Debezium 이 내보내는 이벤트의 실제 필드와 op 코드
    • car 의 1:1 복제와 computer 의 변환 적재가 갈리는 지점
    • 순서 역전, 소프트 삭제, 재기동 중복 처리 세 가지 방어 장치
    • 각 단계를 확인하는 SQL 과 지표 이름

    다루지 않는 것

    • 스키마 변경(DDL) 전파 — 이 파이프라인은 컬럼 추가를 따라가지 않습니다
    • 다중 인스턴스 운영 — 슬롯 하나에 컨슈머 하나가 전제입니다
    • 외래키가 걸린 테이블의 적용 순서 — 현재 두 테이블 모두 FK 가 없습니다
    • 초기 스냅샷의 성능 튜닝 — snapshot.mode=initial 기본값 그대로입니다

    전제

    ./scripts/up.ps1 로 스택이 올라가 있고 http://localhost:56080/actuator/health 가 UP 이어야 합니다. source 는 wal_level=logical 로 기동되어 있어야 하고, 그렇지 않으면 엔진이 슬롯을 만들지 못한 채 기동에 실패합니다.5

    01확인해야 할 다섯 가지

    "동기화가 된다"는 말은 검증할 수 없습니다. 아래 다섯 문장은 그대로 테스트 이름이 되도록 썼습니다.

    정상 흐름

    SC-01 · car 에 넣은 한 건이 값 그대로 target 에 나타난다

    Given
    source car 에 EV6 가 없다
    When
    INSERT INTO car (name, brand, price) VALUES ('EV6','Kia',58900000.00) 가 커밋된다
    Then
    target car 에 같은 id 로 price = 58900000.00, created_at 까지 동일한 행이 1개 생긴다

    SC-02 · computer 에 넣은 한 건은 변환되어 적재된다

    Given
    source computer 에 ('Apple','MacBook Air 15','M4',16,1299.00) 을 넣는다
    When
    이벤트가 ComputerSyncHandler 에 도달한다
    Then
    target 에 full_name = 'Apple MacBook Air 15', spec = 'M4 / 16GB', price_krw = 1753650, deleted = false 인 행이 생긴다

    예외 흐름

    SC-03 · computer 의 DELETE 는 행을 지우지 않고 deleted 로 표시한다

    Given
    target computer 에 id = 3 이 있다
    When
    source 에서 DELETE FROM computer WHERE id = 3 이 실행된다
    Then
    target 행은 남아 있고 deleted = true, source_lsn 이 삭제 시점 값으로 갱신된다. 행 수 정합성은 WHERE deleted = false 로 센다

    SC-04 · 오래된 LSN 을 가진 이벤트는 최신 값을 덮어쓰지 못한다

    Given
    target computer.source_lsn = 26713904 이다
    When
    source_lsn = 26711048 인 이벤트가 재처리된다
    Then
    UPSERT 의 WHERE 절이 걸려 갱신 행 수가 0 이고, full_name 과 price_krw 가 변하지 않는다

    SC-05 · 서비스를 재기동해도 스냅샷이 다시 돌지 않는다

    Given
    offsets.dat 에 마지막 오프셋이 flush 되어 있다
    When
    컨테이너를 재시작한다
    Then
    로그에 WAL resume position 이 찍히고, 중단 지점부터 이어서 읽는다. target 행 수는 변하지 않는다

    2026-08-27 기동에서 실제로 관측된 값

    재기동 직후 로그는 First LSN 'LSN{0/1979408}' received 와 WAL resume position 'LSN{0/19794B0}' discovered 를 남겼고, 스냅샷 없이 스트리밍으로 바로 진입했습니다. SC-05 는 이 로그로 충족됩니다.8

    02구조와 처리 순서

    박스를 끌어 배치를 바꿀 수 있습니다. 배치가 마음에 들면 JSON 버튼으로 내보내 이 파일의 dgm-data 블록에 붙여넣으십시오.

    무엇이 무엇과 통신하는가

    한 건이 지나는 단계와 빠져나가는 길

    오른쪽 아래 점선은 더 이상 유실이 아닙니다

    예전에는 ChangeEventService 가 sink 예외를 삼키고 다음 이벤트로 넘어갔습니다 — 파이프라인은 멈추지 않았지만 그 한 건은 영영 사라졌습니다. 지금은 실패를 재시도 · 격리 · 정지 세 갈래로 나눕니다. 일시 장애는 배치 재시도로 풀고, 개별 데이터 문제는 cdc_dead_letter 로 격리하며, 구조 문제면 오프셋을 전진시키지 않고 멈춥니다. 격리된 건은 유실이 아니라 추적되는 미반영이라 원인을 고친 뒤 재처리할 수 있습니다. 자세한 기준은 docs/pipeline-overview.html 05~06 항목에 있습니다.2

    03엔진이 내보내는 이벤트의 실제 모양

    여기서 오해가 자주 생깁니다. Kafka 를 쓰지 않지만 이벤트 포맷은 Kafka 를 쓸 때와 같습니다. 달라지는 것은 전달 경로뿐입니다.

    엔진 설정에서 세 가지를 껐고, 그 결과 이벤트가 아래처럼 얇아집니다.1

    설정값그래서 이벤트가 어떻게 되나
    converter.schemas.enablefalse거대한 schema 블록이 빠지고 payload 내용만 남는다
    decimal.handling.modestringNUMERIC 이 base64 바이트가 아니라 "58900000.00" 문자열로 온다
    tombstones.on.deletefalseDELETE 뒤에 붙는 null 메시지가 생기지 않는다
    car 에 EV6 를 INSERT 했을 때 오는 이벤트 (구조는 코드 기준, 값은 SC-01 기준)
    {
  "before": null,                        // INSERT 이므로 이전 이미지 없음
  "after": {
    "id": 1001,
    "name": "EV6",
    "brand": "Kia",
    "price": "58900000.00",          // decimal.handling.mode=string
    "created_at": "2026-08-27T02:15:12.481Z",
    "updated_at": "2026-08-27T02:15:12.481Z"
  },
  "source": {
    "table": "car",                  // 이 값으로 sink 를 고른다
    "lsn": 26713904,                 // WAL 위치. 10진수다
    "ts_ms": 1787796912481             // source 커밋 시각. 지연 계산의 기준
  },
  "op": "c"
}

    코드가 실제로 꺼내 쓰는 필드는 이 여섯 개가 전부입니다. 나머지는 파싱 단계에서 버려집니다.2

    필드ChangeEvent 필드쓰이는 곳
    source.tabletablecar 인가 computer 인가로 sink 분기. 그 외 이름은 경고 로그 후 건너뜀
    opopUPSERT 할지 DELETE 할지 결정. r c u d 외에는 통째로 무시
    beforebeforeDELETE 때 id 를 여기서 꺼낸다. REPLICA IDENTITY FULL 이라 전체 컬럼이 들어 있다
    afterafterUPSERT 할 값 전체
    source.lsnlsncomputer.source_lsn 에 저장되어 순서 역전 판정의 기준이 된다
    source.ts_mssourceTsMscdc_end_to_end_lag_seconds 계산. 현재 시각에서 이 값을 뺀다

    op 코드 네 가지

    op의미car 처리computer 처리
    r최초 스냅샷 읽기UPSERTUPSERT (LSN 가드 통과 필요)
    cINSERTUPSERTUPSERT
    uUPDATEUPSERTUPSERT
    dDELETE물리 DELETE소프트 삭제 (deleted = true)

    r 과 c 를 같은 코드로 처리하는 것이 핵심입니다

    스냅샷과 INSERT 를 하나의 멱등 UPSERT 로 처리하기 때문에, 오프셋 파일을 잃어 스냅샷이 다시 돌아도 target 이 깨지지 않습니다. 분기를 나눴다면 재스냅샷마다 중복 키 오류가 났을 것입니다.3

    04car 와 computer 가 갈리는 지점

    같은 이벤트가 source.table 하나로 완전히 다른 경로를 탑니다. 이 대비가 이 프로젝트의 학습 목적 자체입니다.

    car · 스키마가 같을 때

    변환이 없습니다. 값을 그대로 넣고, 충돌하면 그대로 덮어씁니다.3

    JpaCarRepository · CarJpaRepository (JPA · QueryDSL)
    INSERT INTO car (id, name, brand, price, created_at, updated_at)
VALUES (?, ?, ?, ?::numeric, ?::timestamptz, ?::timestamptz)
ON CONFLICT (id) DO UPDATE SET
    name       = EXCLUDED.name,
    brand      = EXCLUDED.brand,
    price      = EXCLUDED.price,
    created_at = EXCLUDED.created_at,
    updated_at = EXCLUDED.updated_at
-- 조건절이 없다. 늦게 도착한 오래된 이벤트도 그대로 덮어쓴다.

    car 에는 순서 방어가 없습니다 — 의도된 대비입니다

    엔진이 단일 스레드로 WAL 순서를 그대로 전달하므로 현재 구성에서는 역전이 일어나지 않습니다. 인스턴스를 둘로 늘리거나 sink 를 병렬화하는 순간 car 는 곧바로 깨지고 computer 는 버팁니다. 확장을 검토한다면 이 표가 그 대가입니다.

    computer · 스키마가 다를 때

    컬럼 이름도 개수도 타입도 다릅니다. 매핑은 SQL 이 아니라 Java 쪽에서 일어나고4, target 에는 원본에 없던 컬럼 세 개(deleted, source_lsn, synced_at)가 추가로 붙습니다.6

    source 컬럼target 컬럼변환 규칙
    brand, modelfull_namebrand + " " + model
    cpu, ram_gbspeccpu + " / " + ram_gb + "GB"
    price_usdprice_krwBigDecimal × 1350, HALF_UP 로 소수점 0자리
    (없음)deletedDELETE 이벤트에서 true 로 세운다
    source.lsnsource_lsn이벤트의 WAL 위치를 그대로 저장
    (없음)synced_at반영 시각 now()
    ComputerJpaRepository.java:38 · UPSERT 의 마지막 한 줄이 전부다
    INSERT INTO computer (id, full_name, spec, price_krw, deleted, source_lsn, synced_at)
VALUES (?, ?, ?, ?::numeric, false, ?, now())
ON CONFLICT (id) DO UPDATE SET
    full_name  = EXCLUDED.full_name,
    spec       = EXCLUDED.spec,
    price_krw  = EXCLUDED.price_krw,
    deleted    = EXCLUDED.deleted,
    source_lsn = EXCLUDED.source_lsn,
    synced_at  = EXCLUDED.synced_at
WHERE EXCLUDED.source_lsn > computer.source_lsn   -- 이 줄이 SC-04 를 보장한다
    JpaComputerRepository · 삭제도 UPDATE 다 (QueryDSL)
    UPDATE computer
SET deleted = true, source_lsn = ?, synced_at = now()
WHERE id = ? AND source_lsn < ?
-- 물리 삭제하면, 늦게 도착한 UPDATE 가 행을 되살려 유령 데이터가 남는다.

    source_lsn 은 사람이 읽을 수 있는 값입니다

    BIGINT 로 저장되지만 16진수로 바꾸면 그대로 PostgreSQL 의 LSN 표기가 됩니다. 2026-08-27 관측 시점에 target computer.id = 2 의 source_lsn = 26713904 이었고, 이는 0/1979F30 으로 같은 순간 슬롯의 confirmed_flush_lsn 과 정확히 같은 값이었습니다.7 즉 "target 이 어디까지 따라왔는가"를 target 테이블만 보고도 알 수 있습니다.
    target 에서 바로 확인
    SELECT id, full_name, source_lsn,
       to_hex(source_lsn) AS lsn_hex   -- 0/ 뒤에 붙이면 슬롯 값과 비교된다
FROM computer ORDER BY source_lsn DESC LIMIT 5;

    05경계 조건과 점검 항목

    평소에는 보이지 않다가 한 번에 손실로 나타나는 지점들입니다. 항목을 클릭하면 체크 상태가 브라우저에 저장됩니다.

    경계 조건

    상황그대로 두면 생기는 일현재 대응
    서비스를 오래 내려둠 슬롯이 붙잡은 WAL 이 계속 쌓여 source 디스크가 고갈된다. 슬롯은 만료되지 않는다 대응 없음. down.ps1 -Wipe 로 볼륨째 내리거나 슬롯을 수동 삭제해야 한다
    sink 에서 JDBC 예외 그 한 건이 유실된다. 재시도도 DLQ 도 없다 cdc_sink_errors_total 증가. 대시보드 경보로만 감지
    1000건을 한 트랜잭션으로 INSERT 커밋 시점에 1000개 이벤트가 한꺼번에 흘러 지연 그래프가 튄다 단일 스레드 순차 UPSERT. 순서는 안전하지만 처리량 상한이 여기서 결정된다
    순서 역전 (재처리, 병렬화) 오래된 값이 최신 값을 덮어쓴다 computer 만 source_lsn 가드로 방어. car 는 무방비
    DELETE 후 같은 id 재사용 소프트 삭제된 행이 되살아나며 deleted 가 false 로 바뀐다 LSN 이 더 크므로 의도된 동작. 다만 삭제 이력은 남지 않는다
    NUMERIC 정밀도 double 로 다루면 환산 금액이 어긋난다 decimal.handling.mode=string 과 BigDecimal 로 전 구간 고정
    source 에 DDL 변경 새 컬럼은 이벤트에 실려 오지만 sink 가 무시하고, target 스키마는 그대로다 대응 없음. 이 문서 범위 밖 (00 항목 참고)

    손대기 전 확인 0 / 0

    • 실습 종료 후 슬롯을 회수했는가남겨두면 source 디스크가 조용히 찬다. 09 항목의 명령 참고
    • cdc_sink_errors_total 이 0 인가0 이 아니면 이미 유실된 건이 있다는 뜻이다
    • car 와 computer 의 행 수를 서로 다른 기준으로 세고 있는가computer 는 반드시 deleted = false 조건이 붙어야 한다
    • 병렬화나 인스턴스 증설을 검토 중인가그렇다면 target car 에 source_lsn 가드를 먼저 넣어야 한다
    • cdc_user 권한이 REPLICATION 과 SELECT 로 제한되어 있는가CDC 계정에 쓰기 권한을 주지 않는다. 원천을 건드릴 수 있게 된다
    • 이벤트 로그에 개인정보가 실릴 수 있는가파싱 실패 시 이벤트 JSON 전문이 error 로그에 그대로 남는다

    06단계별로 어디를 보면 되는가

    "안 넘어온다"는 신고를 받았을 때 위에서부터 차례로 짚습니다. 각 줄은 그 단계가 살아 있는지 판정합니다.

    단계확인 대상보는 방법정상 판정
    1 커밋source 에 값이 실제로 있는가SELECT * FROM car ORDER BY id DESC넣은 행이 보인다
    2 디코딩슬롯이 살아 있고 밀리지 않는가pg_replication_slotsactive = t, lag 이 수 KB 이하
    3 수신엔진이 이벤트를 받았는가cdc_events_total{table,op}INSERT 직후 카운터가 증가
    4 반영sink 가 실패하고 있지 않은가cdc_sink_errors_total0 을 유지
    5 지연커밋에서 반영까지 얼마나 걸리는가cdc_end_to_end_lag_seconds1초 미만
    6 정합성양쪽 행 수가 맞는가아래 대조 쿼리차이 0
    2단계 · source 에서 슬롯 상태 (지연의 90%가 여기서 드러난다)
    SELECT slot_name, plugin, active,
       confirmed_flush_lsn,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), confirmed_flush_lsn)) AS lag
FROM pg_replication_slots;

-- 2026-08-27 관측: embedded_cdc_slot | pgoutput | t | 0/1979F30 | 328 bytes
-- active = f 이면 cdc-service 가 붙어 있지 않다는 뜻이다. 앱 로그부터 본다.
-- lag 이 MB 단위로 커지면 컨슈머가 밀리고 있거나 죽어 있다.
    6단계 · 정합성 대조 (source 와 target 에서 각각 실행)
    -- source (sourcedb)
SELECT 'car' AS t, count(*) FROM car
UNION ALL SELECT 'computer', count(*) FROM computer;

-- target (targetdb) : computer 는 반드시 deleted 조건을 붙인다
SELECT 'car' AS t, count(*) FROM car
UNION ALL SELECT 'computer(active)', count(*) FROM computer WHERE deleted = false;

    여기서 자주 새는 곳

    target 의 computer 를 SELECT count(*) 로 그냥 세면 소프트 삭제된 행까지 포함되어 항상 source 보다 많게 나옵니다. 2026-08-27 실행에서도 물리 행은 5개, active 는 4개였습니다. 정합성 스크립트를 새로 쓸 때 이 조건을 빠뜨리는 것이 가장 흔한 실수입니다.

    09내릴 때와 되돌릴 때

    이 스택에서 되돌리기가 필요한 대상은 애플리케이션이 아니라 source DB 에 남는 슬롯입니다.

    1
    앱 먼저
    cdc-service 를 내려 슬롯 점유를 푼다. DB 를 먼저 내리면 재접속 루프가 돈다
    2
    모니터링과 DB
    exporter, Prometheus, Grafana, source, target 순서로 정지
    3
    볼륨 판단
    데이터를 유지할지, 스냅샷부터 다시 볼지 결정한다
    4
    슬롯 확인
    볼륨을 남겼다면 슬롯도 남아 있다. WAL 이 쌓이는지 확인한다
    상황별 명령
    # 데이터 유지하고 정지 (다음 기동 시 오프셋부터 이어서 읽는다)
./scripts/down.ps1

# 볼륨까지 삭제 (슬롯·오프셋·데이터 전부 소멸, 다음 기동은 스냅샷부터)
./scripts/down.ps1 -Wipe

# 스택은 살려둔 채 슬롯만 강제 회수해야 할 때
podman exec emb-cdc-source-pg psql -U postgres -d sourcedb \
  -c "SELECT pg_drop_replication_slot('embedded_cdc_slot');"
# 주의: active 인 슬롯은 삭제되지 않는다. cdc-service 를 먼저 정지시켜야 한다.

    되돌리기 기준

    target 이 오염되었다고 판단되면 애플리케이션을 고치는 것보다 down.ps1 -Wipe 후 재기동이 빠릅니다. 스냅샷(op = r)이 전체를 멱등 UPSERT 로 다시 채우므로 target 은 source 와 동일해집니다. 운영 환경이라면 이 선택지가 없으므로, 그 전에 cdc_sink_errors_total 경보를 먼저 붙이십시오.

    04V2. 프로세스가 죽었다 살아나는 경우는 유실이 없습니다

    Provider 를 정지시키고, 그동안 원본에 1,000건을 넣은 뒤 재기동했습니다.

    측정결과의미
    다운 중 발생한 변경1,000 건—
    재기동 후 수신1,000 / 1,000유실 0건
    슬롯이 붙잡은 WAL200.2 KiB이만큼이 지워지지 않고 남는다
    변경 1건당 WAL 증가165 bytes허용 다운타임 산출의 기준값
    max_slot_wal_keep_size-1상한 없음

    허용 다운타임 산출

    측정된 165 bytes/건을 기준으로, 원본 변경 속도와 디스크 여유에서 다음과 같이 나옵니다.

    허용 다운타임 계산
    허용 다운타임(초) = 디스크 여유(bytes) / (초당 변경 건수 x 165)

-- 예: WAL 파티션 여유 50 GiB, 피크 1,000 TPS 인 경우
53,687,091,200 / (1,000 x 165) = 약 325,376 초 = 90 시간

-- 예: 같은 여유, 피크 10,000 TPS 인 경우
53,687,091,200 / (10,000 x 165) = 약 32,538 초 = 9 시간

    이 계산은 상한이 없을 때만 유효합니다

    현재 max_slot_wal_keep_size = -1 이라 슬롯이 디스크를 다 채울 때까지 WAL 을 붙잡습니다. 원본 DB 가 디스크 고갈로 멈추는 것이 CDC 유실보다 훨씬 큰 사고입니다. 운영에서는 상한을 걸고, 상한에 걸리면 슬롯이 무효화되어 V3 상황이 되도록 두는 편이 낫습니다 (09 항목).

    05V3. 되받을 수 없는 구간은 두 겹으로 탐지됩니다

    06V4. 중복은 실제로 오지만 두 번 반영되지 않습니다

    Debezium 은 at-least-once 입니다. 오프셋을 기록하기 전에 죽으면 그 구간이 다시 옵니다. 이것은 결함이 아니므로, 막을 대상은 "중복 수신"이 아니라 "중복 반영"입니다.

    측정결과의미
    1차 수신200 건—
    재기동 후 수신200 건전부 재전송됨
    그중 중복(같은 LSN)200 건at-least-once 확인
    1차 반영 행 수200정상 반영
    2차 반영 행 수0가드가 전부 차단
    두 번 반영된 행0이중 반영 없음
    이중 반영을 막는 한 줄
    INSERT INTO ... VALUES (...)
ON CONFLICT (id) DO UPDATE SET ...
WHERE EXCLUDED.source_lsn > sink.source_lsn

-- 같거나 오래된 LSN 이면 갱신 행 수 0 으로 조용히 차단된다.
-- 조회 후 비교가 아니라 한 문장 안에서 판정되어야 한다 —
-- 나누면 그 사이에 다른 이벤트가 끼어들 수 있다.

    검증 방식에 관한 정직한 기록

    처음에는 프로세스를 강제 종료(kill)해 재현하려 했으나, 복제 연결이 늦게 끊겨 재기동이 슬롯을 잡지 못했습니다(수신 0건). 재현 대상은 "죽는 방식"이 아니라 "오프셋이 뒤처진 채 재기동되는 상태"이므로, 오프셋 파일을 이전 지점으로 되돌려 그 상태를 결정적으로 만들었습니다. 재생되는 코드 경로는 동일합니다.

    07V5. 대용량 필드는 REPLICA IDENTITY 설정에 따라 판독 여부가 갈립니다

    PostgreSQL 은 큰 값을 행 밖(TOAST)에 저장하고, UPDATE 에서 그 컬럼이 바뀌지 않았으면 WAL 에 새 값을 싣지 않습니다.

    설정afterbefore현재 값 복원
    REPLICA IDENTITY DEFAULT 자리표시자 없음 불가능
    REPLICA IDENTITY FULL 200,000 bytes 200,000 bytes 가능

    DEFAULT 에서 after 자리에 오는 값은 __debezium_unavailable_value 라는 자리표시자입니다. "값이 안 바뀐 것"과 "값을 못 받은 것"을 구분할 수 없다는 점이 위험합니다 — 그대로 수신 측에 쓰면 실제 데이터가 자리표시자 문자열로 덮어써집니다.

    측정으로 확인된 해소 방법

    ALTER TABLE ... REPLICA IDENTITY FULL 로 전환하면 after 와 before 양쪽에서 200,000 bytes 전체가 판독됐습니다. 관심 필드가 대용량 텍스트나 JSON 이라면 이 설정은 선택이 아니라 필수입니다.

    대가

    FULL 은 UPDATE/DELETE 마다 이전 행 전체를 WAL 에 기록합니다. V2 에서 측정한 165 bytes/건은 이미 FULL 상태의 값이며, 대용량 컬럼이 있는 테이블에서는 이 값이 크게 올라갑니다. 관심 테이블에만 선별 적용하고, 적용 후 WAL 증가율을 다시 측정하십시오.

    08V6. 대사는 검출하고, heartbeat 는 설정 조합이 결정적입니다

    대사 — 건수만으로는 부족합니다

    상황대사 결과비고
    정상 동기화일치300 / 300, 체크섬 0a826cc7... 동일
    수신 측 3건 삭제불일치건수차 3건으로 검출
    건수 동일, 값만 변조불일치체크섬으로만 검출된다
    대사 쿼리 — 양쪽에서 실행해 비교
    SELECT count(*)::bigint AS row_count,
       coalesce(md5(string_agg(
           id || '|' || biz_key || '|' || amount || '|' || status, ',' ORDER BY id)), '') AS checksum
FROM <테이블>
WHERE <대사 범위 조건>;

-- 건수만 비교하면 "지워지고 다른 게 들어온" 경우를 놓친다.
-- 전체 테이블 md5 는 대용량에서 비싸므로 운영에서는 시간 구간으로 잘라 돌린다.

    heartbeat — 간격만 켜면 아무 효과가 없습니다

    관심 테이블에 변경이 없는 동안 다른 테이블이 WAL 을 만들도록 두고, 슬롯이 얼마나 전진하는지 측정했습니다.

    설정슬롯 전진량결과
    heartbeat.interval.ms 만 0 bytes 전진하지 않음 · 붙잡은 WAL 104 에서 108,064 bytes 로 증가
    위 + heartbeat.action.query 38,112 bytes 전진함 · 붙잡은 WAL 7,264 bytes 로 유지

    이것이 이번 검증에서 가장 놓치기 쉬운 발견입니다

    heartbeat.interval.ms 를 켜 두면 안심하기 쉽지만, 관심 테이블에 변경이 없으면 커넥터가 받을 메시지 자체가 없어 확인 지점을 올릴 근거가 없습니다. heartbeat.action.query 로 관심 테이블 집합 안에 주기적으로 WAL 을 만들어 줘야 슬롯이 전진합니다. 실적 발생이 뜸한 시간대가 있는 시스템에서는 이 설정이 없으면 WAL 이 계속 쌓입니다.

    03캡처 계층 — 설정 하나하나에 이유가 있습니다

    기본값을 그대로 두지 않은 항목만 적습니다. 나머지는 Debezium 기본값입니다.2

    설정값그렇게 한 이유
    plugin.namepgoutputPostgreSQL 10+ 내장. 확장 설치가 필요 없다
    publication.autocreate.modedisabledinit SQL 이 대상 테이블을 명시적으로 정한다. 커넥터가 임의로 늘리지 못하게
    snapshot.modeinitial최초 1회 전량 적재 후 스트리밍. 재동기화 절차가 이 값에 의존한다
    tombstones.on.deletefalseKafka 로그 압축용 null 메시지가 불필요하다
    decimal.handling.modestringNUMERIC 이 base64 대신 "1234.56" 로 온다. BigDecimal 로 무손실 복원
    converter.schemas.enablefalse거대한 schema 블록을 제거해 이벤트를 얇게 만든다
    offset.flush.interval.ms10000재기동 시 되돌아가는 최대 구간이다. 중복은 무해하므로 낮출 이유가 적다
    name${CDC_NAME}오프셋 저장 키. 같은 DB 에 커넥터를 둘 이상 붙일 때 겹치면 서로 덮어쓴다
    topic.prefix${CDC_TOPIC_PREFIX}커넥터 정체성. 겹치면 지표·JMX 이름이 충돌한다

    REPLICA IDENTITY FULL 이 전제입니다

    관심 테이블 두 개 모두 REPLICA IDENTITY FULL 입니다. 이것이 없으면 세 가지가 동시에 무너집니다.

    • 필드 단위 변경 식별 불가 — before 에 기본키만 실린다
    • 소프트 삭제 불가 — DELETE 의 before 에서 매핑에 필요한 컬럼을 꺼낼 수 없다
    • 대용량 필드 판독 불가 — TOAST 대상 컬럼이 자리표시자로 온다 (검증 V5)

    대가는 WAL 증가입니다. 측정값이 변경 1건당 165 bytes 이며, 이미 FULL 상태의 수치입니다.6

    연산방식그 방식이어야 하는 이유
    car UPSERTJPA save() 변환도 순서 조건도 없다. 가장 단순한 방식으로 충분하다

    computer UPSERT네이티브 SQL JPA 로도 QueryDSL 로도 표현할 수 없다5
    ComputerJpaRepository.java:38 — 이 한 줄이 네이티브를 강제한다
    INSERT INTO computer (...) VALUES (...)
ON CONFLICT (id) DO UPDATE SET ...
WHERE EXCLUDED.source_lsn > computer.source_lsn

-- 대체 수단인 merge() 는 SELECT 후 INSERT/UPDATE 두 문장이라
-- 위 조건이 "조회해서 비교한 뒤 갱신"으로 벌어진다. 그 사이에 다른 이벤트가 끼어들 수 있다.

    트랜잭션 경계

    BatchApplier.applyAll 이 배치 적용과 진행 지점 기록을 한 트랜잭션으로 묶습니다. 커밋되면 둘 다, 롤백되면 둘 다입니다 — 갈라져 있으면 "적용은 됐는데 어디까지 했는지 모르는" 창이 생깁니다.3

    진짜 병목은 왕복 횟수입니다

    같은 target DB 에 5만 행을 배치 한 문장으로 UPSERT 하면 142ms, 즉 초당 352,000행입니다. JDBC 대 JPA 차이(6,200 대 4,500행/초, 28%)보다 배치화의 이득이 훨씬 큽니다.7

    05실패를 세 갈래로 나눕니다 — 이것이 유실 0의 핵심입니다

    모든 실패를 격리하면, target DB 를 재기동하는 30초 동안 전체 트래픽이 DLQ 로 쏟아집니다. 그건 격리가 아니라 옮겨 담은 것입니다.

    판정 기준은 SQLState 입니다

    스프링의 예외 계층은 쓸 수 없습니다 — 커넥션 실패를 뜻하는 DataAccessResourceFailureException 이 NonTransient 밑에 있어서, instanceof 로 가르면 커넥션 장애가 격리 대상이 됩니다.9

    판정SQLState해당 상황
    재시도 08* · 40001 · 40P01 · 53* · 55P03 · 57* 커넥션 끊김, 직렬화 실패, 데드락, 자원 부족, 잠금 대기, DB 재기동 중
    DLQ 22* · 23* 제약 위반, 형식 오류, 값 범위 초과 — 몇 번을 넣어도 똑같이 실패한다
    정지 28* · 3D* · 3F* · 42* 테이블 없음, 컬럼 없음, 권한 없음 — 모든 이벤트가 같은 이유로 실패한다

    처음에는 격리하며 DLQ 를 기록하고 마지막에 정지를 판단했습니다. 그 결과 정지 후 원인을 고쳐 재기동하면, 되살아나 정상 적용된 건이 DLQ 에도 남아 회계가 어긋났습니다(15 대 12). 멈출 상황이면 애초에 개별 데이터 문제가 아니므로 격리해서는 안 됩니다. 비율 판정을 DLQ 기록보다 앞으로 옮겨 해결했습니다.8

    06DLQ 는 유실이 아니라 추적되는 미반영입니다

    그 차이를 증명하는 것은 회계입니다. target + 미반영 = source 가 성립하면 유실이 없습니다.

    항목내용
    저장 위치수신 측 DB 의 cdc_dead_letter 표. 새 인프라 컴포넌트 없음
    보관 내용table · op · lsn · before · after 전체 + 실패 사유 + SQLState + 시도 횟수
    직렬화 방식Debezium 원문이 아니라 도메인 값을 직렬화한다. 이벤트 포맷이 바뀌어도 재처리가 깨지지 않는다
    기록 트랜잭션REQUIRES_NEW — 실패한 적용의 롤백에 휩쓸리면 안 된다

    왜 수신 측 DB 인가

    별도 저장소에 두면 "적용도 실패, 격리 기록도 실패"가 진짜 유실이 됩니다. 같은 DB 에 두면 DB 가 살아 있는 한 기록이 남고, DB 자체가 죽었다면 그건 08* 로 분류되어 재시도 경로로 빠지므로 오프셋이 전진하지 않습니다. 어느 쪽이든 유실 경로가 생기지 않습니다.

    상태 흐름

    cdc_dead_letter.status
    격리        PENDING            // 자동으로는 집지 않는다
사람 조치   RETRY_REQUESTED    // 원인을 고친 뒤 명시적으로 신청
성공        RESOLVED
실패        PENDING            // attempts 증가, 사유 갱신
포기        DISCARDED

    PENDING 을 자동 재시도하지 않는 것이 핵심 설계입니다. 원인이 고쳐졌는지는 사람만 압니다. 자동으로 돌리면 고쳐지지 않은 독성 건이 주기마다 영원히 재시도되며 로그와 지표를 오염시킵니다.10

    재처리 신청 — 운영자가 실행
    -- 1. 무엇이 왜 막혔는지 본다
SELECT id, source_table, op, source_lsn, failure_sql_state,
       left(failure_message, 120) AS 사유, attempts, status,
       payload::json->'after' AS 값
FROM cdc_dead_letter
WHERE status = 'PENDING' ORDER BY id;

-- 2. 원인을 고친 뒤 재처리를 신청한다 (다음 주기에 자동 처리)
UPDATE cdc_dead_letter SET status = 'RETRY_REQUESTED' WHERE id = 1;

-- 3. 되살릴 수 없다고 판단하면 명시적으로 버린다
UPDATE cdc_dead_letter SET status = 'DISCARDED' WHERE id = 1;

    재처리가 안전한 이유 — 그리고 한 가지 예외

    격리된 뒤 같은 행에 더 새로운 변경이 이미 반영됐다면, 오래된 LSN 을 든 재처리 이벤트는 WHERE EXCLUDED.source_lsn > computer.source_lsn 에 걸려 갱신 행 수 0 으로 차단됩니다. 순서가 뒤바뀐 재처리가 최신 값을 덮어쓰지 않습니다.

    car 는 예외입니다

    그 가드는 computer 에만 있습니다. car 는 조건 없는 UPSERT 라 재처리가 더 새로운 값을 덮어쓸 수 있습니다. 재처리 전에 그 사이 변경이 없었는지 확인해야 합니다. 근본 해결은 target car 에도 source_lsn 컬럼을 두는 것이지만, 그러면 "car 는 source 와 스키마가 동일"이라는 이 프로젝트의 대비 구조가 깨집니다.

    엔진이 멈추고 로그에 격리 비율 격리 비율이 임계를 넘었다 (n/m = x%) 구조 문제. 수신 측 테이블·컬럼·권한을 확인한다. 고치고 재기동하면 멈춘 배치가 되살아난다

    행 수가 계속 안 맞음 대사 쿼리에 deleted 조건이 있는지 computer 는 소프트 삭제라 WHERE deleted = false 가 필수. 가장 흔한 실수
